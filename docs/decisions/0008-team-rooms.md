# ADR-0008：团队房间 —— 不做多人共享一个 DSH；先把"所有者 + 设备"这一层做扎实

- 状态：已接受
- 日期：2026-09-14
- 决策影响：产品边界（`docs/product/mvp.md` § 三、§ 六）、`crates/dr-dsh-daemon`、`docs/security.md`

## 背景

产品定义 § 16 把"团队房间、多用户共享一个 DSH"列为开放问题，M6 的目标里也提到"团队房间"。这条决策要说
清楚**为什么现在不做**，以及将来做的前置条件，否则它会被反复提议。

现有的授权模型是**单一所有者**的：

| 事实 | 位置 |
| :--- | :--- |
| 房间密钥的持有者就是房间的所有者；配对是所有者授予设备的过程 | `drdshd pair` / `crates/dr-dsh-crypto/src/pairing.rs` |
| 设备登记表是房间级的白名单，没有角色概念 | `crates/dr-dsh-crypto/src/registry.rs` |
| 每台设备只有一个权限位：`may_control`（能否下发生命周期命令） | `dr_dsh_proto::control::DeviceSummary` |
| 撤销是整设备撤销（没有"只读设备"的中间态） | `drdshd devices --revoke` |
| 隧道建立后，客户端的**任何** DSH 界面操作都经代理到达 DSH，daemon 不解析它们 | `crates/dr-dsh-daemon/src/proxy`、`docs/security.md` § 2.5 |

最后一行是这条决策的核心：`may_control` 限制的只是**生命周期命令**。一个"只读设备"仍然能把 DSH 界面
的每一个请求发过去——包括在界面里改配置、发消息、跑工具。也就是说，**今天不存在"只读协作"这回事**，
只有"能连"和"不能连"。

## 决策

**M6 不做多人共享一个 DSH；"团队房间"不作为交付物。** 保持"一个房间一个所有者，所有者授予设备"的模型，
并把这一条写进产品边界（`mvp.md` § 三的"不包含"表）。

将来若要支持，前置条件是这三条**同时**具备，缺一条都不做：

1. **角色模型**：至少"所有者 / 可操作 / 只读"三档，且**只读必须由 daemon 强制**——由于代理层不解析
   DSH 的语义，"只读"只能实现为"只允许 GET/HEAD 与少数明确的安全路径"，或者由 DSH 自己提供多用户权限。
   在没有第二条路之前，只读是个谎言。
2. **审计能回答"谁做的"**：审计事件要带设备 id（ADR-0012 定的格式已经为此准备），并且要覆盖**代理面的
   写操作**，否则事后无法追溯谁改了配置。
3. **DSH 侧的多用户能力**：DSH 的会话与工作区是单用户的；多人共享一个 DSH 进程意味着共享同一个工作区、
   同一份凭据、同一批本地文件。这不是本仓库能在代理层修好的东西。

## 被否决的方案

### 把同一个房间密钥发给多个人

- 否决理由：无法撤销其中一个人（撤销要换密钥、所有人重新配对）；没有审计；任何一个人的设备被攻破等于
  整个房间暴露。它还有一个更隐蔽的问题：所有人共享一个房间 id，中继能看到"同一房间有几条客户端连接"
  （`/healthz` 的 room 数），这本身就是团队成员活动的元数据。

### 让多台设备共用一个 daemon，靠 `may_control` 当"只读/可写"两档

- 否决理由：如背景所述，`may_control` 只挡生命周期命令。宣称这是"只读成员"会让所有者以为对方只能看，
  而对方实际上能在 DSH 界面里做任何事——**一个让人误判自己权限的授权模型，比没有授权模型更危险**。

### 每个成员各跑一个 daemon，共享同一个 DSH 进程

- 否决理由：一个 DSH 进程只有一个端口、一份凭据、一个工作区；多个 daemon 去附着它要么抢端口，要么把
  attach 模式变成"多所有者"（attach 模式按设计拒绝生命周期操作，正是因为它不知道进程是怎么起来的）。
  更根本的是，谁能 `stop` 一个共享进程这个问题没有答案。

### 用"共享房间 + 每设备一条流"从协议上支持多人

- 否决理由：这正是 M2 之后一直没做的"每客户端独立流"。它解决的是**传输**上的多客户端问题（当前一条
  carrier 只承载一个会话，最后一个客户端离开就释放 daemon），并不解决**授权**问题。做完它，团队房间
  仍然缺角色与审计——即上面那三条前置条件。

## 后果

### 正面

- 不去实现一个自己都无法诚实描述权限的模型；"所有者 + 已配对的设备"这个模型小而可验证。
- 审计与撤销的语义保持清晰：撤销一台设备就是撤销一台设备。
- 省下的工程量用在 M6 真正能落地的两项（多实例、推送边界）上。

### 负面与代价

- "团队共享"这个诉求被明确拒绝，可能让一部分用户失望。文档要把理由写清楚，并指出替代路径
  （每个人在自己的机器上跑自己的 daemon，通过各自的隧道访问；协作发生在 DSH 的上层，不在本项目的隧道层）。
- `MAX_DEVICES_PER_ROOM = 16` 与 `may_control` 这两个既有设计，将来会被当成角色模型的起点；本条不预先
  扩张它们。

### 需要持续留意

- 如果 DSH 自身将来支持多用户与权限，本条的第三条前置条件就满足了，那时应当重开一条 ADR（而不是改写
  本条）来设计角色模型。
- `may_control` 这个名字在只读角色出现之前是有歧义的，文档里凡提到它都要写明"仅指生命周期命令"。
