# ADR-0009：推送 —— Web Push 不称为端到端；默认通道永远是隧道；去中心化推送排在 M6 之后

- 状态：已接受
- 日期：2026-09-14
- 决策影响：`docs/security.md`（§ 5.4 与新增结论）、`apps/pwa`、`plugins/dr.dsh`、产品定义 § 9.5

## 背景

ADR-0006 已经决定了通知的分级、内容最小化与"推送默认关闭"。本条回答它留给 M6 的那个问题
（`docs/product/mvp.md` § 六）：

> Web Push 的端到端边界：需要确认浏览器推送服务的载荷加密在何种威胁模型下可称为端到端。

要回答它，先把链路上每一跳能看见什么列清楚。Web Push（RFC 8031 的 VAPID + RFC 8291 的载荷加密）把
载荷加密给**用户代理（UA，即浏览器）的密钥**，推送服务（FCM、APNs、Mozilla 的 autopush…）负责转发：

| 谁 | 能看到什么 |
| :--- | :--- |
| 应用服务器（这里是自托管的 daemon 或某个服务） | 明文（它构造推送） |
| 推送服务 | 密文、**以及**元数据：订阅端点、时间、频率、载荷长度、来源 VAPID 公钥 |
| UA 实现方（浏览器厂商，以及它背后可能有的账号体系） | 明文——它持有解密密钥，并且是**代码**（能改、能记录） |
| 用户设备上的其他软件 | 通知到达后的呈现层内容（操作系统通知中心能看到摘要） |

所以"端到端"这个词在这里有一个诱人的误读：**内容对推送服务不可读，但对浏览器厂商不是**。把前者说成
"端到端"是过度声明，而本项目的第一条文档规则就是"不夸大安全性"（`docs/README.md` 的文档约定）。

## 决策

1. **默认且有保证的通知通道永远是已建立的隧道**：daemon 把通知帧发到 PWA（前台或已安装），不经过任何
   第三方。这是唯一被称为"端到端"的通道，因为两端都是本项目的代码与用户自己的密钥。
2. **Web Push 保持可选、默认关闭**（沿用 ADR-0006），并且在所有文档与 UI 里用这句话描述它：
   *"内容对推送服务不可读，但浏览器厂商能看到，因此这不是端到端加密。"* `docs/security.md` § 5.4 必须
   逐字包含这个结论，而不是"启用了加密所以是端到端"。
3. **推送载荷继续结构最小化**：只给事件类型与不透明会话引用（`dr_dsh_proto::control::Notification` 的
   形状），正文在用户打开应用后经隧道取回。理由不只是内容——**长度与频率也是信息**，一个 200 字节的推送
   与一个 20 字节的推送能区分"工具输出"与"审批请求"。
4. **去中心化推送（自托管分发器，例如 UnifiedPush）排在 M6 之后**，触发条件是：有真实用户需要"App 未打开
   也能收到"，并且自托管分发器的部署成本能被一份文档覆盖（当前的安装文档已经有三平台的篇幅预算，不再
   加第四个组件，除非前一条成立）。

## 被否决的方案

### 把 Web Push 描述成端到端

- 否决理由：不成立（见上表）。而且它会造成**静默降级**：用户以为通知内容和隧道里一样受保护，实际上
  多了一个能看到明文的实现方。

### 自建推送服务器作为默认通道

- 否决理由：默认路径引入一个必须常开的第三方（哪怕自建，它也是"另一个必须活着的服务"），与"零配置、
  没有服务器"的既有姿态冲突；而且它并不比隧道通知更私密——它只是把信任从一个厂商换成运营者自己。

### 打开应用才通知，彻底不做推送

- 否决理由：审批请求是**阻塞性**的（ADR-0006 把它定为 `alert`），用户离开电脑十分钟就应当被告知。
  保留一个默认关闭的可选通道，比宣称"不需要"更诚实。

### 用第三方推送 SDK 顺带把账号体系引进来

- 否决理由：见 ADR-0006 的同名条目——这是"为一个功能引入一整套账号体系"的典型来源。

## 后果

### 正面

- 安全声明与实际一致：唯一被称为端到端的通道两端都是本项目的代码。
- 推送的最小化落在数据结构上（协议类型里没有承载正文的字段），可被审计。
- 用户不需要为了用这个项目而注册任何第三方账号。

### 负面与代价

- 关闭推送时，手机在后台不会收到通知——这是默认行为，文档要写清楚"要后台通知就得接受一个更弱的通道"。
- 元数据（频率、长度、时间）仍然会泄漏给推送服务；文档不能只谈内容加密。
- 自托管分发器被推迟，可能让一部分用户长期停留在"更弱的通道或没有通道"这个二选一里。

### 需要持续留意

- 浏览器厂商对推送实现（例如把解密放在哪一层、是否做端侧扫描）的改动会改变上表，需要定期复核，
  而不是一次写死。
- 如果将来真的引入自托管分发器，本条要为它新增一条 ADR（载荷格式、端点发现、失败回退），而不是在
  这里补写。
