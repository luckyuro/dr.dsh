# ADR-0001：语言分工 —— Rust 承载常驻进程，TypeScript 承载 DSH 集成面

- 状态：已接受
- 日期：2026-09-11
- 决策影响：全部组件

## 背景

dr.dsh 需要长期驻留在用户电脑上的两个组件（本地代理、中继服务），以及必须与 DSH 生态直接交互的组件（DSH 插件、Web 远程客户端）。上游 DSH 是 TypeScript / Cordis 项目，且明确声明处于 developer preview、会有破坏性变更。

语言选择因此不是"喜好"问题，而是两个相互冲突的约束：

1. **常驻进程的约束**：本地代理要在用户机器上 7×24 运行，要处理加密、要管理子进程、要在旧硬件上启动。它需要小的常驻内存、确定的崩溃行为、单文件分发、无运行时依赖。
2. **集成面的约束**：与 DSH 交互的唯一受支持缝隙是 Cordis bundle 插件，它必须是 TypeScript/Node，且必须能 import DSH 的类型与事件契约。浏览器客户端也只能是 JS。

如果强行统一语言，二者必有一伤：用 TypeScript 写常驻进程要拖着 Node 运行时并接受其内存与启动成本；用 Rust 写插件则需要非官方的 FFI 或子进程桥接，直接违反"不修改 DSH 核心、插件式集成"。

## 决策

**按"谁常驻、谁隔离"划分语言，而不是按仓库划分。**

| 组件 | 语言 | 理由 |
| :--- | :--- | :--- |
| 中继服务 | Rust | 公网可达、承载全部用户的密文流量；崩溃与内存行为必须可预测，且它必须是**可审计的小二进制** |
| 本地代理 `drdshd` | Rust | 常驻用户机器；管理子进程、做加密、做反向代理，全部是 Rust 生态的强项 |
| wire 协议（规范性定义） | Rust 定义 + TS 镜像 | 两端实现必须逐字节一致，用共享向量强制（ADR-0004） |
| E2E 加密（浏览器侧） | TypeScript | 只能跑在浏览器里；用 WebCrypto，不自己实现密码学原语 |
| DSH 插件 | TypeScript / Node | 唯一受支持的 DSH 集成缝隙就是 Cordis bundle 插件，没有第二个选择（ADR-0003） |
| 远程客户端 PWA | TypeScript | 浏览器 |
| 运维脚本、文档工具 | TypeScript / Node | 与 DSH 贡献者技能集一致 |

关键点在于：**Rust 与 TypeScript 之间没有共享代码，只有共享规范。** 两端的接触面是两个长期存在的契约：

- **wire 协议**：`crates/dr-dsh-proto` 定义，`packages/protocol` 镜像，共享向量文件强制一致。
- **DSH 事件与 HTTP 面**：插件通过 loopback HTTP 把事件报告给 daemon；daemon 通过 loopback HTTP 代理 DSH。二者都是普通的网络契约。

这带来一个刻意的后果：**加密逻辑必须实现两遍。** 这是本决策最贵的部分，接受它的理由是它换来了两个更强的性质：浏览器端不需要信任任何 Rust/WASM 产物，daemon 端不需要信任 JS 运行时。

## 被否决的方案

### 全 TypeScript / Node

- 否决理由：常驻进程的可靠性是产品承诺之一（自愈、崩溃率 < 0.5%）。Node 进程的内存曲线、启动延迟、以及"必须随 Node 版本演进而升级"的运维负担，都会直接转嫁给用户。
- 更具体地：本地代理要在用户的旧笔记本上开机自启并长期驻留。Rust 二进制在这种场景下的确定性是可交付的承诺，Node 不是。

### 全 Rust（插件与 PWA 用 WASM 或 FFI 桥接）

- 否决理由：违反"不修改 DSH 核心、插件式集成"。Cordis 插件必须是 ESM 模块；把 Rust 塞进去需要 WASM 边界或子进程桥接，两者都会把上游破坏性变更的影响面从"一个文件"扩大到"一套绑定层"。

### Go / Rust 混用（中继 Go、代理 Rust）

- 否决理由：中继与代理共享 wire 协议实现（`dr-dsh-proto`），其中继侧要解析帧、做流控路由。分语言意味着协议实现也要分叉成三份，而协议一致性是本项目最不能出错的地方。中继的部署优势（Go 的静态二进制）Rust 同样具备。

## 后果

### 正面

- 常驻组件无运行时依赖，可单文件分发、可交叉编译（`rust-toolchain.toml` 声明了目标平台）。
- 中继的依赖闭包可以被审阅并被工具检查（`cargo tree -p dr-dsh-relay`），"零知识"从承诺变成可检查的构建属性。
- DSH 破坏性变更的影响面被限制在 TypeScript 侧的一个模块（`plugins/dr.dsh/src/dsh-surface.ts`）。
- 密码学在两端都使用成熟实现：RustCrypto 与 WebCrypto，不自行实现原语。

### 负面与代价

- 两套工具链（cargo + pnpm），贡献者门槛更高。缓解：`pnpm run verify` 一条命令跑完全部检查；文档 `docs/development/contributing.md` 给出最短路。
- 加密实现存在两份，必须靠共享向量而非"看起来一样"来保证一致。缓解：见 ADR-0004，向量文件是规范性文件，两端 CI 都校验。
- 无法在两端之间共享类型定义。缓解：把共享物降级为规范文本 + 向量文件，而不是试图共享代码。

### 需要持续留意

- 如果 DSH 未来提供稳定的进程外事件通道（例如 SDK 支持附着到运行中的实例），插件这一层的存在理由会被削弱，届时应当重新评估 TypeScript 侧的范围。见 `docs/integration/dsh-surface.md`。
