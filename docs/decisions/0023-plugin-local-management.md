# ADR-0023：插件页面、本机授权与独立管理作业

- 状态：已接受
- 日期：2026-10-29
- 决策影响：DSH 插件、原生 CLI、daemon 代理、插件打包
- 接续：[ADR-0022](0022-plugin-managed-daemon-foundation.md) 的后续阶段；保留其配置、归属和运行时接口决策

## 背景

用户希望安装一个 DSH 插件包后，在 DSH 页面完成 daemon 安装、配置、配对和维护。
ADR-0022 已提供结构化 CLI 与私有运行时接口，但仍缺少三个边界：浏览器如何取得本机管理权，
停止 DSH 的操作如何在插件消失后完成，以及如何把当前手动启动的宿主安全交给 daemon。

DSH 的 cookie、Host/Origin 检查不能独立证明请求来自本机操作者：正常远程代理也持有有效
DSH cookie，并使用 loopback authority。因此不能把一个通过 DSH 鉴权的页面直接变成安装器。
插件也不能靠退出回调或普通后台子进程保证更新完成；托管服务停止时会连同它们一起消失。

## 决策

1. **插件提供页面，原生程序执行管理。** 页面位于 `/_drdsh/manage`，通过闭集 JSON 操作调用
   原生管理层。`daemon.json` 仍是唯一配置来源；插件只持久保存实例 prefix 引用、授权文件和
   native 缓存。DSH 服务、profile、路由和启动生命周期假设仍只写在 `dsh-surface.ts`。
   管理子树按可选服务挂载，失败或热重载不破坏事件报告，也不能使 DSH 启动失败。
2. **单包携带匹配平台的 native。** DSH 安装包可以包含 Linux x86_64 musl、macOS arm64
   的原生程序与清单。插件先检查目标、版本、所有者和文件类型，再复制到包目录以外的私有缓存；
   缓存校验 SHA-256。页面不接收 native 下载 URL、包源、prefix 或任意 shell 命令。
   当前页面缺少随包 native 时明确失败，不静默改用旧 Release。bootstrap 底层的可选下载只允许
   受信任配置指定的固定 GitHub Release 版本、受限 HTTPS 跳转及 SHA-256 校验，不接受 `latest`。
3. **本机管理有独立授权。** 静态页面和 API 首先执行 DSH 原有鉴权，并要求真实 loopback
   连接；写请求还要求精确同源 Origin 和 JSON。解锁需要默认位于用户私有数据目录的 `0600`
   capability 文件，或本机浏览器的一次性启动链接。显式点击打开本机浏览器时，链接只交给 OS
   opener，并写入私有文件作为无桌面环境的回退；API 不返回链接秘密。启动链接有效 5 分钟、
   单次使用，换出的管理 Bearer 会话有效 15 分钟，DSH 重启或插件卸载后失效。
4. **隧道不能到达管理命名空间。** daemon 在 HTTP 转发和 WebSocket 升级前共同拒绝
   `/_drdsh` 与其子路径。检查先分离 query，再做有界多层 percent 解码和点目录归一；控制字符、
   非法转义与超限明确拒绝。普通查询中出现管理路径不影响路由。DSH 看到有效 cookie 或
   loopback 地址不替代这道隔离，报告令牌也不赋予管理权。
5. **跨宿主退出的操作交给 OS 作业。** 安装、更新、卸载、服务切换和会终止 DSH 的生命周期
   操作通过 `job.submit` 提交。Linux 使用用户级 systemd 作业，macOS 使用 launchd；作业有
   私有持久记录、稳定的 job ID、独立执行器和同 prefix 的互斥。页面只轮询保存结果；页面断线
   不代表成功，重开后可查询。旧同步 CLI 保留，受管宿主内的危险同步调用仍拒绝，不能靠删除
   `DRDSH_MANAGED_INSTANCE` 标记绕过。
6. **首次接管只针对已确认的当前宿主。** 页面先按当前 profile、目录和端口准备 daemon 安装，
   不抢占仍由手动 DSH 使用的端口。`handoff.plan` 从调用链识别实际宿主，记录 PID、进程开始
   身份和配置约束；用户明确提交该计划后，由独立作业重新验证身份、停止这一个宿主，再启动
   已保存的 daemon 服务。浏览器不能提交任意 PID；身份变化、端口不符或计划失效都拒绝。
   普通 attach 模式继续拒绝远程 stop/restart，不能自动转成接管。
7. **插件与服务有各自生命周期。** 插件安装的 daemon 固定采用 `external` 归属，并启用本机
   管理和报告；daemon 更新或卸载不删除 DSH 拥有的插件。插件热重载、卸载只释放页面和会话，
   不据此停止 daemon。停止 DSH 后页面也停止，独立 daemon 与已提交 OS 作业可以继续运行；
   页面重新可达需先恢复 DSH。

## 被否决的方案

- **仅检查 loopback、Origin 或 DSH cookie。** 这些也是正常代理请求的形状，无法区分远端
  已配对设备与本机管理者。管理 capability 与代理命名空间拒绝必须同时存在。
- **把解锁秘密注入 DSH 首页、通用 RPC 或 API 响应。** 远端界面可以读取这些渠道。首页只放
  固定非秘密入口，秘密只经过本机文件或本机浏览器交接。
- **让安装器注册回自己的插件，或把 native 缓存放进插件目录。** 前者产生递归归属，后者会
  在插件更新、卸载时删除正在运行的执行器。外部归属和稳定私有缓存分别解决这两个问题。
- **用 `spawn(..., detached: true)` 充当持久作业。** 它不能跨 systemd 服务组的终止保证存活，
  也没有可恢复的状态。OS 管理器不可用时应具名失败，不能回落成一个看似成功的后台进程。
- **按浏览器传来的 PID 杀进程，或直接杀占端口的进程。** PID 会复用，端口也可能属于其他
  应用。首次接管必须由本机原生代码识别当前宿主并在执行前重新校验。

## 后果

用户可以通过一个 DSH 包取得页面与原生管理器，保留原有终端入口和独立 daemon。中继、
远程 wire、密码学与共享向量不改变；本机页面不成为新增的远程管理通道。

代价是多了一组 DSH Web 服务契约、短期授权状态、原生包校验和平台作业生命周期。
管理面目前只按 DSH `0.2.1-rc.2` 的契约验证；旧版报告兼容不等于管理页面兼容。
Linux 需要用户 systemd 会话，macOS 需要用户 launchd 会话；不承诺原生 Windows 管理。

SHA-256 提供完整性检查，不替代签名、可复现构建或第三方审计。DSH 插件、同用户进程及其
执行的工具仍在本机信任边界内；本机授权不能隔离已经能读取该用户文件的恶意代码。
作业记录保证可以查询结果，不意味着所有中断都可自动重放，失败后仍须按状态处理。

使用步骤和协议见[插件页面与本机管理](../operations/daemon-management.md)。
