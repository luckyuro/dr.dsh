# ADR-0011：托管中继 —— 代码不为托管化预埋数据收集；运营规则是运营者的事

- 状态：已接受
- 日期：2026-09-14
- 决策影响：`crates/dr-dsh-relay`、`docs/product/mvp.md` § 三/§ 六、`docs/operations/self-hosting.md`

## 背景

`docs/product/mvp.md` § 三把"托管中继"排在 M4，M4 的剩余项里写着"托管化运营规则（配额、限流、投诉
通道）"；§ 六又把它列为未决。技术门槛其实不高——自托管与托管运行同一份二进制，协议不区分部署形态
（`crates/dr-dsh-relay` 没有与此相关的开关）。真正的门槛是：

1. **运营主体**：谁承担滥用责任、谁处理投诉、谁为流量付费；
2. **滥用处置**：配额、限流、封禁，以及"封禁"在零知识中继里意味着什么（中继只能看到房间 id 与连接
   元数据，它没有任何内容可用于判定）；
3. **合规**：不同司法辖区对"转发加密流量"的要求不同。

这三条没有一条能由代码仓库决定。相反，如果为了"将来可能托管"而在中继里预埋能力（IP 日志、房间 id
持久化、按账号的连接历史），**自托管用户会立刻承担这些能力的代价**——这是本条要防的事。

## 决策

1. **自托管是唯一支持的形态。** 托管服务不在路线图上；`mvp.md` § 三保持"托管中继：需要先回答商业
   模式、运营主体、滥用处置"这一表述，且不给出时间表。
2. **中继不新增任何为托管化预埋的数据收集**：不持久化 IP、房间 id、连接历史；不引入账号或配额表；
   `/healthz` 只报聚合数字（房间数、容量上限），这条已经是现状（`crates/dr-dsh-relay/tests/routing.rs`
   里"health 计数但从不点名房间"的断言固定了它）。任何试图在中继里加日志字段的改动都要先推翻本条。
3. **限流留在"单机自托管"的合理默认上**，也就是现在已有的三样：`DSH_RELAY_MAX_ROOMS`（默认 1024）、
   帧长上限（`MAX_FORWARDED_PAYLOAD`，与协议上限一致）、每房间 16 个客户端。**不做按 IP 的限流**：
   中继看到的 IP 是反向代理的 IP，要拿到真实来源就得信任 `X-Forwarded-For`，而那正是我们不允许中继
   信任的东西（它会变成一个可伪造的、影响服务可用性的输入）。
4. **托管化若要发生**，前置交付物是一份独立的运营文档（配额取值、投诉通道、封禁流程、日志与保留、
   合规声明），由运营者署名；那时再开一条 ADR 记录它，而不是把能力先塞进代码。

## 被否决的方案

### 现在就实现按 IP 的连接与房间配额

- 否决理由：在没有托管服务的前提下，它主要伤害合法用户（同一个 NAT 后面的家庭、办公室、咖啡馆），
  而且需要一个可信的来源 IP——只有让中继信任代理头才能得到，这会新增一个可伪造输入与一条"中继必须
  正确解析 HTTP 头"的责任。真要做，也应该在反向代理层做（那里本来就知道真实来源，也本来就在做 TLS）。

### 在中继里记录房间 id（或房间数的时间序列）以便运营

- 否决理由：房间 id 是房间密钥的单向派生值，本身不是密钥，但它**是跨时间的关联标识**——持久化它等于
  给"谁在什么时间用了这个中继"留下了一份可被传票调取的记录。中继保持贫瘠是它的安全属性（ADR-0002），
  运营便利不足以推翻它。

### 把托管做成默认形态，自托管作为高级选项

- 否决理由：与项目存在的理由相反（"访问你自己电脑上的 DSH"）。而且默认托管意味着默认有一个能看到
  元数据的第三方，这条要在威胁模型里被反复解释，成本远高于收益。

### 用配额表 + 账号体系换取"免费额度"

- 否决理由：账号体系会把一个无状态的中继变成一个持有用户数据（邮箱、付款、连接历史）的服务，
  合规义务随之全部上线。这与本项目"没有服务器"的姿态正面冲突。

## 后果

### 正面

- 自托管用户拿到的是同一份贫瘠的中继：没有需要关闭的日志、没有需要删除的账号、没有需要接受的条款。
- 中继的审计面保持很小（`crates/dr-dsh-relay` 的依赖闭包与源码扫描已经在 `zero_knowledge.rs` 里固定）。
- 托管化被明确为"运营问题"，不会被误当成代码缺口。

### 负面与代价

- 没有官方托管服务，第一次使用的门槛高于"点一下就用"的产品；这是自托管的固有代价，缓解方式是文档
  （Docker 一键部署已交付、旧 CPU 的构建路径已交付）。
- 没有按 IP 限流意味着一个恶意客户端可以占满 `MAX_ROOMS` 或耗尽单个房间的连接数。当前边界是：每房间
  16 客户端、1024 房间、单帧 64 KiB；这挡住了内存无限增长，但挡不住"占满房间数"这种拒绝服务。
  使用者在公网上暴露中继前应当知道这一点——`self-hosting.md` 的容量一节要写明。

### 需要持续留意

- 如果将来真的出现托管服务，本条的第三条（不做按 IP 限流）要在**中继之外**解决：由运营者的边缘层
  （CDN、负载均衡、反向代理）承担，这样自托管与托管可以在同一份二进制上共存而不让前者承担代价。
- `/healthz` 的聚合数字是当前唯一的运营仪表盘；如果托管化发生，它需要扩展，但那属于运营文档的范畴。
