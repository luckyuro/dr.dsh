# ADR-0007：多实例 —— 一个 daemon 一个 DSH；同机多实例靠多个 daemon，客户端记住多个房间

- 状态：已接受
- 日期：2026-09-14
- 决策影响：`crates/dr-dsh-daemon`、`apps/pwa`（设备记录与连接状态）、`docs/operations/install.md`

## 背景

产品定义 § 16 把"一个 daemon 管理多个 profile/实例"列为开放问题，M6 的目标里写着"多设备/多 daemon 管理"。
必须先分清三个不同的诉求，它们常被混为一谈：

1. **一台电脑上跑两份 DSH**（工作 / 个人两个 profile，或两个项目用不同配置）。
2. **一台设备连多台电脑**（手机同时连着家里的台式机与公司的笔记本）。
3. **一群人连同一台电脑**（团队共享）——那是 ADR-0008，不在本条。

现有实现里，下列事实决定了选择的空间（都有代码或测试固定）：

- `SupervisorConfig { executable, port }`：**一个 daemon 监督一个 DSH 进程**，端口由 daemon 自己选
  （`crates/dr-dsh-daemon/src/dsh/supervisor.rs`）。
- 一个 daemon 持有**一个房间密钥**、一个房间 id、一个设备登记表、一条 carrier 连接
  （`crates/dr-dsh-daemon/src/uplink.rs`）。
- 中继的房间语义是 **1 个 daemon + 最多 16 个客户端**（`MAX_DEVICES_PER_ROOM`），而一条 carrier 只承载
  **一个客户端会话**（盐交换是按连接做的：`Transport::establish` 的文档写明了原因）。
- 两个 daemon 配同一个房间密钥会互相顶替，实测代价约每秒 3 次请求（`uplink.rs` 里那段注释记录了
  284 → 175 次/分钟的测量），**它是配置错误，不是多实例机制**。

## 决策

**一个 daemon 进程 = 一个 DSH 实例 = 一个房间。** 同机多实例通过运行多个 daemon 进程实现，每个进程有
独立的 `DSHD_STATE_DIR`、房间密钥、DSH 端口；daemon 不引入任何实例路由层。

具体到实现与文档：

1. `DSHD_STATE_DIR` 是实例的身份（设备登记表、房间密钥、崩溃报告、审计日志都在里面）。安装文档要给出
   两个实例并列的最小示例：两个 systemd 用户单元、两个状态目录、两个 `--port`。
2. PWA 侧把"当前设备记录"扩展为**一个设备身份 + 每房间一条记录**：身份密钥（Ed25519）在浏览器里只有
   一份，房间密钥与房间 id 按房间各存一份。原因是身份是"这台设备"的概念，而授权是"这个房间的所有者
   授予的"；把身份也按房间复制会让 `drdshd devices` 里出现同一台手机的多个身份，人无法核对。
3. 客户端 UI 增加一个房间列表（每项：名字、最后连接时间、连接状态），一次只连一个房间——同时保持多条
   隧道意味着 N 份控制面状态与 N 份代理会话，收益（同时看两块屏幕）远小于复杂度。

## 被否决的方案

### 一个 daemon 管多个 DSH 实例

- 否决理由：控制面、登记表、房间密钥、生命周期驱动都要带上"哪个实例"，而**每多一个维度就多一组
  越权可能**（远端能不能用一个实例的凭据操作另一个？撤销一个设备是否影响全部实例？）。这条路的收益是
  "少起几个进程"，代价是把当前最清晰的边界（一个 daemon 只服务一台 DSH，`docs/security.md` § 2.3）
  换成一张权限矩阵。多起一个进程已经能工作，且隔离更彻底（崩溃、端口、版本互不影响）。

### 用一个房间密钥跑多个 daemon，客户端二选一

- 否决理由：两个 daemon 会互相顶替房间，每次顶替都让已在线的客户端掉线（relay 释放 carrier 后客户端
  必须重做盐交换）。这是被实测量化过的配置错误，不能当成功能。

### 一个房间挂多个 DSH，由 daemon 扇出

- 否决理由：中继的 room 语义与"一条 carrier 一个会话"的既有契约都建立在一对一上；改成扇出要么改协议
  （每客户端独立流——M2 就列为未做的事），要么让 daemon 在同一会话里多路复用两个 DSH 的代理流量
  （authority、cookie、升级路径会互相污染）。这两条都比"再起一个 daemon"贵得多。

## 后果

### 正面

- 零协议改动、零新增攻击面：实例隔离就是进程隔离与状态目录隔离。
- 与现有测试一致（多 daemon 顶替的测量、单会话 carrier 的契约），不需要推翻任何已固定的性质。
- 每个实例可以有自己的 DSH 版本与配置，这在本机开发场景里正是用户想要的。

### 负面与代价

- 资源按实例线性增长：每个实例一个 node 进程 + 一份状态目录；32 位老机器上的预算要写进文档。
- 用户要管多把房间密钥与多次配对。缓解：ADR-0013 让密钥首次运行自动生成并落盘，用户不再需要接触它；
  但**每个房间仍要单独配对一次**，因为授权是按房间的。
- PWA 的记录模型要改（一条记录 → 一个身份 + 每房间条目），并且要处理"同一个房间被换过密钥"这种陈旧
  条目的清理。

### 需要持续留意

- 若 DSH 将来支持"一个进程多 profile"，本条要重新评估：那时"多实例"的边界可能上移到 DSH 内部，
  daemon 只需多传一个参数。
- 房间列表是客户端第一次持有"多台电脑"的状态，要小心它别变成同步后端——列表只存本地，永不上送。
