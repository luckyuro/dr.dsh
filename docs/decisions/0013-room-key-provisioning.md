# ADR-0013：房间密钥 —— 首次运行生成并落盘 0600，命令行仍可覆盖但不写盘

- 状态：已接受
- 日期：2026-09-14
- 决策影响：`crates/dr-dsh-daemon`（`run` / `pair` 的密钥解析）、`docs/operations/install.md`

## 背景

`docs/product/mvp.md` § 六把它列为未决，并写清了两种做法各自的代价：

> 房间密钥的配置方式：`drdshd run` 与 `drdshd pair` 现在都要显式给出 `--room-key`，而且必须是同一个值。
> 它足够安全（不写进单元文件、不出现在日志里），但要求操作者保管一把密钥并在两个命令里各给一次。
> 可选的做法是 daemon 首次启动时生成并写入 `$DSHD_STATE_DIR/room-key`（0600），之后 `run` 与 `pair`
> 都从那里读……**尚未决定**，因为两种做法都能讲清楚，而选错的那个会把"两个来源不一致"变成一个安静的
> 配置错误。

这正是现状的失效模式，而且**已经被观察到**：`run` 与 `pair` 给成不同的密钥时，设备拿到的是一把没人
认的钥匙，现象是 `no daemon is serving this room`——它既不提密钥，也不提是哪一个环节错了。
（`docs/operations/install.md` 的"装好之后"一节点名了这个坑，这本身就是它足够常见的证据。）

同时，配对的存在改变了密钥的角色：**配对之后，房间密钥不再是人需要接触的东西**——它由配对回执密封后
交给设备，设备之后按它推导房间；房间密钥从此主要是一个"身份根"，而不是一张要抄写的口令
（`crates/dr-dsh-crypto/src/pairing.rs`、`drdshd pair-as-device` 写出的 `device.json`）。

## 决策

1. **首次运行生成并落盘。** `drdshd run` 或 `drdshd pair` 在既没有 `--room-key`、状态目录里也没有
   `room-key` 文件时，生成 32 字节随机密钥，写入 `$DSHD_STATE_DIR/room-key`（**0600**），并打印
   **路径而不是密钥**："`generated a room key at <path>`；用 `drdshd pair` 把设备加进来"。
   不打印密钥的理由：终端回滚、`journalctl`、粘贴到 issue 里，都是它的泄露路径；而用户从不需要看到它。
2. **解析顺序**：`--room-key` > 状态目录的 `room-key` 文件。状态目录由 `DSHD_STATE_DIR` 决定
   （多实例就是多目录，见 ADR-0007）。
3. **命令行提供的密钥不写盘。** 覆盖是"这次运行用这把"，不是"把这把设成默认"——否则命令行（会进
   shell 历史）就成了密钥的写入路径。启动横幅要说明当前用的是哪一种来源，让"两个来源不一致"变成
   可见的事实。
4. **不一致时出声。** 若 `--room-key` 与状态目录里的文件不同，启动时打印一条明确的提示
   （"using the key from the command line; the stored key at <path> is different and was not changed"）。
   不自动覆盖、不静默选一个：这正是背景里那个安静的配置错误。
5. **`drdshd room-key` 保留**，但文档把它定位成"需要手动管理密钥时的工具"，而不是安装步骤的必经之路。

## 被否决的方案

### 继续要求显式给出 `--room-key`

- 否决理由：它把最容易出错的一步留给了用户，而失效方式是安静的（`no daemon is serving this room`）。
  安全上它并不更好：密钥要么在命令行（进 shell 历史）、要么在环境变量（`systemctl cat` 会打印
  `Environment=` 行，`install.md` 已经警告过）、要么在文件里。既然最终都要落到文件，就让 daemon
  自己写，且写对权限。

### 把密钥写进配置文件

- 否决理由：配置文件在本仓库的定义是"可以安全粘贴进 bug report 的明文"（`crates/dr-dsh-daemon/src/config.rs`
  的模块文档）。密钥一旦允许出现在那里，那条定义就守不住了。

### 只支持环境变量

- 否决理由：systemd 单元的 `Environment=` 行会被 `systemctl cat` 与 `systemctl show` 打印，macOS 的
  LaunchAgent plist 是明文 XML，Windows 的计划任务参数在事件日志里——三平台都有一条"看起来私密、
  实际会被打印"的路径。文件 + 0600 是唯一在三个平台上语义一致的做法。

### 把密钥写进状态目录并**同时**打印它

- 否决理由：打印没有任何使用者（配对码才是给人看的），却新增三个泄露面（终端回滚、日志、粘贴）。
  "生成时打印一次"是很多工具的习惯，但那些工具的密钥是给人**输入到别处**的；这里的密钥由回执自动
  交付，所以那个习惯没有对应需求。

### 每个房间用同一把密钥（"一个用户一把根密钥，多个房间派生"）

- 否决理由：它把多实例的安全边界绑定在一起（一把泄露，全部房间可推导），而多实例的隔离正是
  ADR-0007 的全部价值。派生结构（HKDF 按房间名派生）看起来优雅，但房间名一旦被中继看到，派生就
  不是秘密了；要保密就得再引入一个秘密，复杂度回到原点。

## 后果

### 正面

- 安装步骤少一步，且最容易出错的"两个命令给同一把密钥"不再可能出错——`run` 与 `pair` 默认读同一个
  文件。
- 用户不需要看到、复制或保管密钥；密钥不再出现在任何命令行或单元文件里。
- 多实例自然而然（每个 `DSHD_STATE_DIR` 一把密钥），与 ADR-0007 一致。

### 负面与代价

- 状态目录成了**唯一的身份根**：删掉它就等于换了一把密钥，所有已配对设备要重新配对。文档必须写明
  这一点，并且安装文档里"备份什么"的答案变成"`$DSHD_STATE_DIR`（它包含设备登记表与房间密钥）"。
- `--room-key` 仍然存在（给需要手动管理密钥的部署），于是"两个来源"这个复杂度没有消失，只是从一个
  安静的失败变成一个会出声的提示。
- 首次运行时生成的密钥在**配对之前**没有任何东西保护它的分发——如果用户在配对前把房间 id 分享出去，
  那与旧流程没有区别。密钥安全仍然依赖"房间 id 是单向派生值"这个事实（它不可反推密钥），以及配对
  本身（SPAKE2）才是授权。

### 需要持续留意

- `drdshd pair` 在**没有**运行过 `run` 的机器上也会生成密钥（它是独立命令）。这是刻意的：先配对后
  运行是合理顺序，而两个命令指向同一个状态目录就会拿到同一把密钥。文档要把这条说明白，避免用户以为
  "必须先 run 一次"。
- 若将来引入托管形态，"密钥由服务端托管"会与本条冲突；那属于 ADR-0011 的范畴，需要新开一条 ADR。
