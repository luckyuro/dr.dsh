# ADR-0012：审计日志 —— 本机 `audit.jsonl`，30 天滚动，只记事件不记内容，永不上送

- 状态：已接受
- 日期：2026-09-14
- 决策影响：`crates/dr-dsh-daemon`（新的 `audit` 模块与 `drdshd audit`）、`docs/security.md` § 4

## 背景

`docs/product/mvp.md` § 六把"审计日志的保留策略"列为未决：*daemon 侧保留多久、本地还是可选上送*。
同时 M1 的剩余项记着一条事实：**审计事件目前只覆盖配对**——

- 已有：`pairing_refused` / `pairing_failed` / `pairing_locked_out` / `pairing_accepted`，一行一条写
  stderr（`crates/dr-dsh-crypto/src/throttle.rs` + `drdshd pair` 的输出，原因文本会替换控制字符并截断）。
- 缺失：隧道建立与断开、设备撤销、生命周期命令。

这些缺失的事件恰好是"谁在什么时候动过这台机器"的答案。没有保留策略，它们只能靠 stderr 重定向，
而 stderr 会进 journald、进 shell 历史、进复制粘贴的 bug 报告。

## 决策

1. **落点与格式**：`$DSHD_STATE_DIR/audit.jsonl`，一行一个 JSON 对象，**0600**，与设备登记表同目录。
   字段固定为：`at_ms`、`event`、`device`（设备 id，若该事件属于某设备）、`outcome`
   （`ok` / `refused` / `failed`）、`reason`（人类可读、已去控制字符并截断）。
   **没有承载 payload、URL、消息正文、文件路径或密钥的字段**——与通知（ADR-0006）和崩溃报告
   （`docs/security.md` § 5.10）同一条最小化规则。
2. **事件集合（闭集）**：`pairing_accepted`、`pairing_refused`、`pairing_failed`、`pairing_locked_out`、
   `device_revoked`、`tunnel_established`（带设备 id，**每次建立都记**）、`tunnel_released`、
   `lifecycle_command`（op 与结果）。集合是闭集：新增事件类型要同时改本节、写入端与读取端。
3. **保留**：最多 **30 天**或 **10 000 行**，先到者为准；写入时滚动删除最旧的整行。
   滚动发生在写入路径上（不是定时任务）：daemon 是一个前台进程，没有 cron 可依赖。
4. **不上送**：审计日志**永不**自动发送到任何地方——不上中继、不上托管服务、不经隧道发给客户端。
   读取方式是本机命令 `drdshd audit [--clear]`，与 `drdshd crashes` 同一套交互。
   要把它交给别人（例如安全事件响应），由用户自己复制——这个动作必须是人的动作。
5. **失败不阻断**：审计写入失败（磁盘满、权限）不得阻断配对或隧道。写失败会打印一次警告并计入
   `drdshd doctor` 的输出，但**不**改为拒绝服务——因为把"日志写不下去"变成"服务不可用"是一种
   可利用的拒绝服务。

## 被否决的方案

### 每条 carrier 建立/断开都写

- 否决理由：隧道会重连（网络切换、代理超时、休眠唤醒），一条日志会在一天里被同一条隧道刷满，
  把真正有价值的配对与生命周期事件淹没。保留 `tunnel_established` / `tunnel_released` 的目的不是
  统计在线时长，而是回答"某台设备在某时刻是否真的连上过"——重连产生的多条记录恰好是它要表达的。
  这也意味着**保留窗口按行数滚动时，噪音会挤掉老事件**——10 000 行的上限是按这个最坏情形定的
  （每 30 秒重连一次也够 3 天以上，正常使用远超 30 天）。

### 写进系统日志（journald / Event Log），由系统负责保留

- 否决理由：系统日志是**可被同机其他用户与系统管理员读取**的（journald 默认按用户隔离，但 root 与
  adm 组可读；Windows 事件日志同理）。审计事件里有设备 id 与"什么时候有人连上了这台电脑"，它属于
  用户自己的数据。写文件并设 0600 是唯一能说清"谁能读"的做法。
- 另有一个工程理由：系统日志没有结构化查询，`drdshd audit` 要读它就得解析自由文本。

### 把审计上送到中继，做"集中审计"

- 否决理由：跨信任边界。中继是零知识的（ADR-0002），上送审计等于自愿给它一份设备活动记录；而且
  中继无法验证这些事件的真实性，集中起来也只是"自称的日志"。真正的集中审计需要一个被信任的第三方，
  那与本项目"没有服务器"的姿态冲突。

### 无上限保留，交给用户自己清理

- 否决理由：审计日志会在用户不知情的情况下长到几十兆，而磁盘满的后果由其他组件承担（崩溃报告、
  登记表写入）。30 天 / 10 000 行是两个都容易解释的数字，且足够回答"上周三晚上有人连过吗"。

## 后果

### 正面

- "谁动过这台机器"有了本机可查、可删除、不上送的答案；撤销设备与生命周期命令也进入同一条时间线。
- 与崩溃报告共用一套交互（`drdshd audit` / `--clear`）与一条最小化规则，用户只学一次。
- 审计格式是闭集，可被测试钉住（`at_ms`/`event`/`device`/`outcome`/`reason` 五个键）。

### 负面与代价

- 隧道事件会产生稳定的日志增长（重连频繁的用户会更快触到 10 000 行），老事件因此被滚动掉。
  接受这个代价，因为审计的价值随时间下降得很快。
- `tunnel_established` 记录了设备 id 与时间，它本身是一份"谁在什么时候用了这台机器"的记录。
  写在本机、0600、可删除，并且用户可以完全关掉审计（见下）。

### 需要持续留意

- 需要一个显式的关闭开关（`DSHD_AUDIT=0`），因为"审计"在某些部署里本身就是敏感的存在
  （例如共用电脑）。关掉时 `drdshd audit` 要说清楚"审计被关闭"，而不是显示"没有事件"——两者
  对排障的含义完全不同。
- 保留策略写死在代码里（30 天 / 10 000 行）是刻意的：可配置的保留策略在实现上意味着一个解析
  错误的窗口，而这两个数字没有需要因部署而异的理由。若将来有，再开一条 ADR。
