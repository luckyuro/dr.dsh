# ADR-0006：通知 —— 先复用 DSH 已有的跨进程通道，推送通道全部可选

- 状态：已接受
- 日期：2026-09-11
- 决策影响：`plugins/dr.dsh`、`apps/pwa`、`crates/dr-dsh-daemon`

## 背景

通知是本项目最容易被做坏的部分，原因有两个：

1. **不是所有事件都应该打断人。** 把每个工具调用都推给手机，等于训练用户忽略通知；产品定义因此要求区分噪音与关键状态（§ 9.5、§ 12）。
2. **推送通道本身是隐私风险。** 通知内容会经过第三方基础设施（APNs、FCM、或自建推送），而"内容最小化"只有落在数据结构上才是真的，写在文档里不算。

调研 DSH 0.1.5-rc.2 后得到一个有利事实：**最要紧的两类通知不需要任何 DSH 侧代码**——Gateway 的跨进程转发事件允许列表（19 项，编译期常量）已经包含 `approval/request` 与 `user-questions/request`，它们经由被代理的 `/api/remote.mux` 就能到达远端。而 `session/event`、`subagent/*`、`goal/changed` 不跨进程。

## 决策

### 1. 分级：三档严重度，写进协议而不是 UI

| 事件 | 报告类型 | 严重度 | 理由 |
| :--- | :--- | :--- | :--- |
| `approval/request` / `user-questions/request` | `approval_requested` | `alert` | 任务被人为阻塞，必须立刻知道 |
| `session/event` → `turn/end` | `turn_complete` | `notice` | 最常见的事件；角标即可，不发声 |
| `goal/changed` → 完成 | `goal_complete` | `alert` | 用户自己设定的目标结束了 |
| `subagent/end` | `subagent_complete` | `info` | 活动信息，不是结果 |
| 生命周期变化 / 隧道断开 | `lifecycle_changed` / `connection_lost` | `notice` / `alert` | 失败必须透明（§ 9.7） |
| `agent/status` | 不上报 | — | 太频繁；仅用于本地 UI 指示 |

这个映射由 `plugins/dr.dsh/src/reporter.ts` 实现，并有单元测试。它是产品决策的落点，不是实现细节。

### 2. 内容最小化落在数据结构上

一条通知只包含：事件类型、严重度、时间戳、以及一个**不透明的会话引用**。数据结构里没有承载消息正文、工具参数、文件路径或模型输出的字段——因此"通知不含敏感内容"不是纪律要求，而是类型系统的事实（§ 9.5）。

会话引用是本地标识符，脱离隧道密钥后无法关联到任何内容；远端 UI 用它把通知定位到正确的会话。

### 3. 推送通道可选，且默认关闭

- 远端的实时通知依赖一条已建立的隧道：daemon 推送通知帧 → 客户端在前台或已安装的 PWA 中展示。这是默认形态，不依赖任何第三方。
- 需要"App 未打开也能收到"时，**可选**启用 Web Push。Web Push 的载荷加密是否真正端到端由浏览器与推送服务共同决定，因此本项目不把它当作安全通道：启用时必须使用一次性、内容最小化的载荷（只给事件类型与会话引用，正文在用户打开后再通过隧道取回）。
- 自托管推送（例如自建 UnifiedPush 分发器）与去中心化通道是目标形态，但排在 M6。

### 4. 关键事件即时，其余可聚合

`alert` 级事件立即上报；`notice` 与 `info` 允许在 daemon 侧做短窗口聚合（例如 30 秒内多个 `subagent_complete` 合并为一条摘要）。聚合策略属于配置，默认保守。

## 被否决的方案

### 用 DSH SDK 的 stdio 通道做通知

- 否决理由：SDK 只提供 4 类通知、没有审批流、且驱动的是**另一个** runtime，无法附着到运行中的 `dsh web`。关键通知恰好是它拿不到的那类。

### 让插件把所有事件都 POST 给 daemon，由 daemon 决定过滤

- 否决理由：那会让每一次工具调用都跨越一次进程边界与 HTTP 调用，给用户的会话增加稳定但无意义的开销。过滤应当尽量靠近事件源（插件内），daemon 只做聚合与转发。

### 默认开启 Web Push

- 否决理由：把推送服务放进默认路径，等于让用户默认依赖第三方基础设施，与 § 5"不强迫用户使用第三方推送通道"冲突。也因此，推送必须显式开启，且开启时要说明它比隧道通知更弱。

### 用第三方推送 SDK 作为唯一通道

- 否决理由：见上的理由，另加一条工程理由：推送 SDK 是最常见的"为了一个功能引入一整套账号体系"的来源。

## 后果

### 正面

- 最要紧的通知（审批、提问）在 M0 就可用，不需要插件。
- 通知的隐私性质由数据结构保证，可被审计。
- 默认路径不依赖任何第三方；推送是一个明确的、可关闭的增强。

### 负面与代价

- 没有插件时，通知种类受限（缺 `session/event`、`subagent/*`、`goal/changed`）。这是有意的分期：先让关键路径零依赖可用，再让丰富度成为可选。
- 聚合窗口意味着 `notice` 级事件可能延迟数十秒。默认保守，且对 `alert` 不生效。

### 需要持续留意

- Web Push 的端到端加密边界需要在 `docs/security.md` 中持续如实描述，不能因为"启用了加密"就声称端到端。
- 如果 DSH 把 `session/event` 加入跨进程转发列表，插件的必要性下降，通知路径应随之简化。
