# 架构决策记录（ADR）

本目录记录**已经做出的、会影响多个组件的决策**：为什么这样选、否决了什么、代价是什么。它是评审时的第一手材料——如果一处设计看起来奇怪，答案通常在这里，而不是在代码注释里。

## 什么时候需要写一条新 ADR

满足其中任意一条：

- 改动跨两个以上组件（例如同时动协议与 daemon）；
- 引入了新的依赖类别，或移除了一个现有的保证；
- 否决了一个看起来更简单的方案，而后来者很可能会再提一次；
- 触及 `docs/security.md` 里任何一条"保证"。

**不需要** ADR 的：实现细节、局部重构、修 bug、加测试、改文档措辞。

## 写法

新建 `NNNN-kebab-title.md`，编号取当前最大值 +1，用下面的骨架。语言与既有 ADR 一致（中文叙述，标识符与路径用英文）。

```md
# ADR-NNNN：一句话结论

- 状态：提议 / 已接受 / 已取代（被 ADR-XXXX 取代）
- 日期：YYYY-MM-DD
- 决策影响：受影响的组件或文档

## 背景
约束是什么；哪些事实（附上游证据或实测结果）迫使必须做选择。

## 决策
做了什么。要具体到"另一个工程师照着能实现"。

## 被否决的方案
每个方案一段，写清**否决理由**。这一节是 ADR 最有价值的部分。

## 后果
### 正面
### 负面与代价
### 需要持续留意
```

## 三条约定

1. **ADR 不可改写。** 决策变了就写新的一条，并在旧的那条顶部标注"被 ADR-XXXX 取代"。历史是有用的：它解释了为什么某个方案当年不成立。
2. **被否决的方案必须留痕。** 一条只写了"我们选了 X"的 ADR，会在半年后被同一个人重新提议 X 的替代品。
3. **代价要写。** 只列好处的 ADR 是宣传材料，不是决策记录。每条 ADR 的"负面与代价"一节都不应为空。
