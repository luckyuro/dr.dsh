# ADR-0002：零知识中继 —— 用依赖图而不是承诺来保证

- 状态：已接受
- 日期：2026-09-11
- 决策影响：`crates/dr-dsh-relay`、`crates/dr-dsh-crypto`、`docs/security.md`

## 背景

产品定义要求"中继服务零知识：中继服务无法读取任何会话内容或控制指令"（§ 8、§ 9.6）。这句话最容易被写成一个无法验证的承诺：中继仍然是代码，代码可以被改动，而"我们没有记录明文"这种说法在审计时毫无价值——它无法被证伪，也无法被持续检查。

同时，中继必须承担真实的转发职责：它有房间、有连接、有流的上行下行、有流量控制、有容量限制。完全不理解任何东西的中继是写不出来的，所以"零知识"必须被精确定义成"**不理解哪些东西**"。

## 决策

**把零知识定义为构建期属性：中继的依赖图中不存在任何能够解密或解释内容的 crate。**

具体地：

1. `crates/dr-dsh-relay` 不依赖 `dr-dsh-crypto`，也不依赖任何密码学 crate（AES-256-GCM、X25519、HKDF 等一概没有）。它没有密钥，因此没有解密的能力，而不是没有解密的意愿。
2. `crates/dr-dsh-relay` 不依赖 `dr-dsh-proto` 的 `control` 模块。它只解析 carrier 帧头（类型、流 id、长度），不解析任何 payload 语义。`dr-dsh-proto` 的模块边界（`frame`/`mux` 对 `control`）就是这条线，`dr-dsh-proto` 的 crate 文档把它写成硬约束。
3. `crates/dr-dsh-relay` 不依赖任何 DSH 包，也不可能"顺手"长出检查 harness 流量的功能。
4. 中继不持久化 payload。它没有数据库、不写 payload 日志、重启即遗忘。运维文档 `docs/operations/self-hosting.md` 明确说明"中继没有值得备份的东西"。

**中继能看到什么，穷举如下**：房间 id、连接与房间的归属关系、帧头（类型、流 id、payload 长度）、以及流量与时序特征。这些是路由必需的最小集合。

**中继不能看到什么**：payload 字节、生命周期指令、会话内容、设备名、文件路径、任何 DSH 数据。

## 强制手段

| 手段 | 检查时机 |
| :--- | :--- |
| `crates/dr-dsh-relay/tests/zero_knowledge.rs`：断言依赖表里没有密码学 crate、没有 `dr-dsh-crypto`，且源码不引用 `dr_dsh_proto::control` | `cargo test`（CI 与本地同一条命令） |
| `cargo tree -p dr-dsh-relay` 的闭包被评审；依赖变更需要说明 | 代码评审 + CI |
| `crates/dr-dsh-relay/Cargo.toml` 中 `dr-dsh-proto` 只被用于帧编解码 | 单元测试：中继的测试只构造帧头与不透明 payload |
| 端到端测试：在真实链路上跑一次会话，断言中继日志与转发的 payload 中不出现明文特征串 | M1 起的 e2e 测试（见 `docs/development/contributing.md`） |
| `#![forbid(unsafe_code)]` | 编译期 |

前两项的分工值得说明：`zero_knowledge.rs` 是一次性的**静态**检查，能在有人加依赖或加 import 的当下就失败；`cargo tree` 是**动态**证据，证明真实解析出来的闭包确实如此（例如传递依赖引入的东西）。两者都要有——静态检查看不懂依赖解析，而依赖评审看不出一行 import。

## 被否决的方案

### 中继持有会话密钥的变体（"端到端加密但中继参与密钥协商"）

- 否决理由：中继一旦参与密钥协商，就拥有了密文之外的攻击面（它可以替换自己的公钥）。这与"中继被完全攻破也不泄露内容"的目标直接冲突。

### 中继解密后做内容路由（例如按 URL 路由到不同房间）

- 否决理由：这是"零知识"最容易被侵蚀的地方——一旦有了解密能力，"临时解密用于调试"就变成一个可提交的 PR。正确做法是把路由信息放在**密文之外的帧头**里（房间 id + 流 id），让中继无需理解内容即可正确路由。

### 用中继做端到端的策略执行（例如"只允许白名单指令通过"）

- 否决理由：中继无法验证白名单，因为它看不懂 payload；而且把安全策略放在中继上，等于要求用户信任中继。白名单必须由 daemon 执行，因为 daemon 是用户自己的机器（§ 9.6）。见 ADR-0003。

## 后果

### 正面

- "中继零知识"变成可检查、可持续验证的性质，可以被写进安全审计的输入，而不是审计的结论。
- 中继可以被部署在用户不完全信任的基础设施上（VPS、朋友的服务器、公共托管服务），仍然不泄露内容。
- 中继的依赖闭包小，攻击面与可维护性同时受益。

### 负面与代价

- 中继无法实现任何需要内容感知的功能：不能做内容级缓存、不能做压缩优化、不能做按内容的告警。这些都是刻意的牺牲。
- 中继无法帮助排查"内容层"的问题。故障定位必须依赖两端的本地日志，这对支持流程提出了更高要求（`docs/operations/troubleshooting.md` 因此格外重要）。
- 帧头仍然泄露流量特征（长度与时序）。这一点在 `docs/security.md` 的非目标与残留风险中如实列出，不做超额声明。

### 需要持续留意

- 任何人都可能提出"让中继顺便做 X"的需求。ADR-0002 的作用就是让这类提案必须显式地推翻一条已记录的决策，而不是在一次 PR 里悄悄发生。
