# ADR-0004：Wire 协议 —— 二进制帧 + 单一规范来源 + 跨语言向量

- 状态：已接受
- 日期：2026-09-11
- 决策影响：`crates/dr-dsh-proto`、`packages/protocol`、`crates/dr-dsh-relay`

## 背景

一条隧道要同时承载：控制指令（状态、生命周期、配对、设备管理）、通知、以及被代理的 DSH HTTP/WebSocket 流量。协议需要满足四个互相拉扯的要求：

1. **中继必须能路由，但不能理解内容**（ADR-0002）：路由所需的信息必须在密文之外，其余全部在密文之内。
2. **实现必须存在于两种语言里**（ADR-0001）：Rust（daemon/relay）与 TypeScript（客户端）。
3. **DSH 的流量形态不可预测**：普通请求、Server-Sent Events、WebSocket 升级、长轮询；未来的 DSH 版本还会加新的流式端点。
4. **移动端网络会断**：协议必须能重连并从断点恢复视图，而不是要求用户刷新。

## 决策

### 1. 两层平面，边界就是信任边界

- **Carrier 平面**（`frame`、`mux`）：定长 18 字节帧头 + 不透明 payload。中继只解析这一层。
- **Payload 平面**（`control` 与 DSH 流量）：端到端加密后才进入 carrier 的 payload。中继无从解析。

帧头布局（大端，固定 18 字节）：

```
 0               1               2               3
+---------------+---------------+---------------+---------------+
|  magic 'D'    |  magic 'R'    |  ver_major    |  ver_minor    |
+---------------+---------------+---------------+---------------+
|         frame_type            |           flags               |
+---------------+---------------+---------------+---------------+
|                        stream_id                              |
+---------------+---------------+---------------+---------------+
|                        payload_len                            |
+---------------+---------------+---------------+---------------+
```

`payload_len` 上限 64 KiB（`MAX_PAYLOAD_LEN`）。上限偏小是刻意的：它迫使复用器交错传输而不是让大传输饿死交互流量，同时限定了恶意对端能让中继缓冲多少内存。读取到超出上限的声明长度时，**只根据帧头就拒绝**，不分配内存。

### 2. 流多路复用，一个连接承载所有客户端

一个 daemon 只维持一条 carrier 连接。客户端发起的流使用奇数 id，daemon 发起的（事件推送）使用偶数 id，流 0 保留给连接级控制（握手、ping）。每条流有独立的流量控制窗口（初始 256 KiB，上限 16 MiB），单连接并发流上限 64，单房间设备上限 16。

限制都写在协议常量里，而不是散落在实现中：这样两端对"什么算越界"有同一份答案，中继可以据此拒绝而不必理解内容。

### 3. Payload 用 JSON，但不承诺永远是 JSON

M0 阶段控制消息是 JSON：体积小、可用浏览器 devtools 直接观察、便于排障。协议版本在帧头里，因此未来可以把热路径（流数据）换成二进制编码，而不改变控制消息的文档形状。**规范来源是 Rust**（`crates/dr-dsh-proto`），TypeScript 侧是镜像（`packages/protocol`）。

### 4. 一致性由共享向量强制，而不是靠评审

`packages/protocol/conformance/vectors.json` 是**规范性文件**：Rust 侧用 `include_str!` 编译进测试二进制，TypeScript 侧用 `node:fs` 读取同一份文件。两端都必须：

- 逐字节解码每一个 `frames` 向量，并逐字节重新编码回原字节；
- 对每一个 `rejections` 向量按指定原因拒绝；
- 对截断输入返回"不完整"而不是错误。

改动任何一个向量都是 wire-breaking change，需要协议版本号变更。这条规则让"两份实现悄悄分叉"变成 CI 上的红灯——这是本项目最不能出错的地方。

### 5. 版本协商：major 不等即拒绝，minor 允许向下兼容

major 不同直接拒绝连接（帧头布局属于 major 的一部分）；minor 是加法式的，对端可以接受更低的 minor，但**不得发送未协商的帧类型**。

## 被否决的方案

### 全部用 WebSocket + JSON

- 否决理由：需要把 DSH 的每一个 WebSocket 帧、每一个 SSE 事件再包一层 base64 或 JSON 字符串，移动网络下的开销与延迟都不可接受；而且中继将不得不解析 JSON 才能路由，违反 ADR-0002 的边界。

### 用现成协议（HTTP/2、QUIC 流、gRPC）

- 否决理由：中继需要的是**在密文之外做最小路由**的能力。HTTP/2 的头部语义会把 URL、Header 暴露给中继（正是我们要避免的），而 QUIC/gRPC 会把中继变成一个必须理解会话语义的端点。自研 18 字节帧头的信息量恰好是路由所需的最小集合，而且可以被完整测试。

### Protobuf / MessagePack 作为 payload 编码

- 否决理由：M0 阶段的可观测性价值高于编码效率，而 payload 已经端到端加密、每帧很小。等出现真实的热路径瓶颈再换（协议已经为此留了版本位），而不是提前优化。

### 让中继做压缩

- 否决理由：压缩密文没有收益，压缩明文需要解密密文——直接违反 ADR-0002。

## 后果

### 正面

- 中继的实现可以做到很小，且它的正确性可以用"只解析帧头"来界定。
- 两端实现的一致性有机械化的保证，而不是靠人工比对。
- 新的 DSH 流式端点无需协议改动即可通过（它们只是同一条流里的字节）。
- 断线恢复有明确的位置：流 id 与序号在帧头，重连后客户端只需重建视图。

### 负面与代价

- 自研帧格式意味着自研流控与错误语义，这是容易出 bug 的地方。缓解：`crates/dr-dsh-proto/src/mux.rs` 的状态机有单元测试，且 M0 的 e2e 测试覆盖乱序注入与超窗注入。
- 帧头泄露长度与时序特征。这在 `docs/security.md` 的残留风险中如实列出。
- 两份实现的维护成本（ADR-0001 已接受此代价）。

### 需要持续留意

- 如果出现第三种语言实现（例如原生移动端），向量文件的价值会更高，届时应当把它作为独立的可发布产物。
