# 安全模型

本文是 dr.dsh 的安全依据。它说明**保证什么、如何被强制、以及不保证什么**。最后一部分与第一部分同样重要：一个不肯说出自己弱点的安全文档，在审计时没有价值。

在信任本项目处理任何东西之前，请先读完第 5 节。

---

## 1. 威胁模型

### 我们在防谁

| 对手 | 能力假设 | 我们的应对 |
| :--- | :--- | :--- |
| **被动网络监听者** | 能看到 daemon 到中继、以及客户端到中继之间的全部流量 | 端到端加密；中继只承载密文 |
| **恶意或被完全攻破的中继** | 可任意读写、丢弃、重排、延迟、重放帧；可记录全部元数据；可拒绝服务；在托管形态下还可向新设备投递客户端代码 | 中继没有密钥，无法解出内容；AEAD + 流内序号使重排、重放、跨流搬运可被检测；见第 5 节关于"投递代码"的诚实说明 |
| **同一局域网内的攻击者** | 可访问用户机器所在的局域网，可做 ARP/ DNS 欺骗 | DSH 始终只监听回环地址；daemon 从不监听对外端口 |
| **持有已配对设备但不知道配对码的人** | 拿到一台已配对的手机或笔记本 | 设备私钥不可导出；可按设备撤销；撤销即时生效 |
| **在配对窗口内猜测配对码的人** | 能在 300 秒内反复尝试配对 | SPAKE2 使**离线**字典攻击不可行；在线尝试必须被速率限制（见第 3 节） |
| **本机上的其他普通用户** | 能在同一台机器上运行进程，但不是管理员 | daemon 的本地状态文件权限为 `0600`；本地控制端点默认仅回环且带令牌 |

### 我们明确不防谁

- **已经控制 daemon 所在机器的攻击者（含 root/管理员）。** 密钥、明文、以及 DSH 本身都在那台机器上，这一层被攻破则一切结束。这是本地优先架构的固有性质，不是本项目的缺陷。
- **DSH 自身的漏洞。** DSH 会在用户的机器上执行模型生成的代码与命令；远程访问让这些能力可以从远处触发。我们的应对是**不扩大** DSH 的暴露面（不改变它的绑定、不绕过它的鉴权），但不声称能修复 DSH 内部的问题。
- **供应链攻击。** Rust 与 npm 依赖都是攻击面。缓解手段是依赖闭包尽量小、中继的闭包被逐个审阅、以及对关键路径做锁定与审计，但这不是保证。
- **浏览器 0-day。** 远程客户端运行在浏览器里。
- **拥有用户解锁设备的攻击者**（未锁屏的手机）。这与"已配对设备"不同：设备已解锁时，任何应用级保护都可以被绕过。

## 2. 信任边界与保证

### 2.1 中继零知识

**保证**：中继服务无法读取任何会话内容、控制指令、设备名或文件路径。

**如何被强制**（不是"我们承诺"，而是"它做不到"）：

- `crates/dr-dsh-relay` 的依赖中**没有任何密码学 crate**，也没有 `dr-dsh-crypto`。它没有密钥，因此没有解密能力。
- 它只解析 18 字节的 carrier 帧头（类型、流 id、长度）以完成路由，不解析任何 payload 语义。`dr-dsh-proto` 的 `frame`/`mux` 模块与 `control` 模块之间的边界就是这条线。
- 它不依赖任何 DSH 包，因此不可能"顺手"理解 harness 流量。
- 它没有数据库、不写 payload 日志，重启即遗忘。
- 检查方式：`cargo tree -p dr-dsh-relay` 的闭包在评审中被逐个确认。任何新增依赖都需要说明理由。

**中继能看到什么（穷举）**：房间 id、连接与房间的归属关系、帧头（类型、流 id、payload 长度）、以及流量与时序特征。

**中继做不到什么**：解密内容；伪造或注入内容（AEAD 会拒绝）；把 payload 搬到另一条流上（帧头作为附加认证数据被绑定进 AEAD）；重放一帧而不被发现（流内 nonce 是递增计数器，重复或跳号都是协议错误）。

**一个例外必须写清楚：配对房间。** 配对发生时还没有共享密钥，而帧总得用某个东西密封，所以配对房间的临时传输根是一个**公开常量**（`dr_dsh_crypto::pairing::transport_root()`），盐也随明文可读的路径交换。**结论是硬的：配对房间上的一切都在中继的阅读范围内**，中继可以解开它、改写它。因此这条规则不是"最好不要"，而是"不允许"：

- 配对码**从不**出现在配对房间的任何帧里——它只是 SPAKE2 的秘密，一个知道房间全部明文的观察者仍然只能在线穷举 2⁴⁰；
- 房间密钥**只在 PAKE 密钥下密封后**出现在回执里（§ 6.2）：PAKE 密钥只有完成了交换的两端持有，中继既推不出也替换不了；
- 回执的 AAD 绑定设备公钥，因此一份被中继复制到另一次配对的回执打不开。

这条边界的检查方式是一个可重跑的测试（`crates/dr-dsh-daemon/tests/pairing.rs` 的
`the_relay_cannot_read_the_room_key_out_of_the_receipt`），它扮演的正是中继：只用公开值连接、读取 daemon 发出的每一帧、断言房间密钥不在其中。

### 2.2 端到端加密

**保证**：只有配对的客户端与 daemon 能解密会话内容。

- 密钥协商：配对时用 **SPAKE2**（平衡 PAKE），以配对码为低熵秘密；此后重连使用**已登记设备密钥**的挑战—应答，不再涉及配对码。
- 会话密钥：由 HKDF 派生的**方向性**密钥（c2d 与 d2c 分离，防止反射）。
- 内容加密：**AES-256-GCM**，96 位 nonce 由 4 字节零 + 64 位大端计数器构成。
- 附加认证数据（AAD）：帧的 stream id，与 `dsh-remote/v1/frame` 标签拼接；这使跨流搬运可被检测。
- Rust 侧用 RustCrypto 的 `aes-gcm`，浏览器侧用 WebCrypto 的 AES-GCM——**同一套密码套件，两份实现**，由共享向量强制一致（ADR-0004）。
- 密钥只在内存中，连接关闭即 zeroize；任何密钥类型都不实现会打印内容的 `Debug`。

**为什么用 SPAKE2 而不是"把配对码哈希成密钥"**：配对码只有 40 位熵，而配对协商必然经过中继。若直接把它当密钥，任何记录到握手的人都可以离线穷举这 40 位。PAKE 让在线猜测成为唯一途径，而在线猜测可以被 TTL、单次使用与速率限制压制。

### 2.3 最小权限与闭集白名单

**保证**：远程端只能触发四种操作，且无法向 DSH 传递任何参数。

- 白名单是**类型层面的闭集**：`LifecycleOp` 只有 `start` / `stop` / `restart`（以及查询状态）。协议里不存在承载"启动参数"的字段，因此不存在注入口。
- daemon 从**自己锁定的配置**启动 DSH，不接受远端传入的可执行路径、端口或标志。
- 没有通用命令执行、没有文件传输、没有远程 shell、没有任意路径读取。

### 2.3.1 中继只提供客户端模块，且按名字拒绝测试模块

中继的 `/client/<module>.js` 是一个**面向任何访问者**的端点，因此它的过滤器是安全边界而不是方便性检查。规则是：

- 只提供**扁平**的 `.js`：拒绝 `..`、绝对路径、反斜杠、`.js` 之外的扩展名（`session.ts`、空名、`.js` 本身）；
- **按名字拒绝测试模块**（`*.test.js`、`*_test.js`）。

第二条不是洁癖：客户端的测试模块里**写死了房间密钥与设备密钥**（它们需要固定的密钥才能断言派生的房间 id），
而 `dist/` 是**累积目录**——构建配置今天排除了测试，但早先构建留下的文件仍然在那里、仍然可被请求。
一个能被陌生人下载的测试模块同时是**密钥泄露**和**在用户浏览器里执行无关代码**。构建脚本现在会先清空 `dist`，
中继也会按名字拒绝；两道都在，因为构建规则可以被遗忘，而请求过滤器不会。

### 2.4 回环绑定

**保证**：DSH 永远不会被本项目绑定到非回环地址。

- daemon 只以一个常量 `127.0.0.1` 访问 DSH；配置结构里**没有** host 字段，因此"改配置绕过"这条路径不存在。
- 启动 DSH 时使用的参数由 daemon 生成，远端无法影响。
- 这与上游 DSH 的立场一致：`dsh web --host 0.0.0.0` 被它自己显式拒绝（理由是"会向网络暴露远程代码执行"）。我们不去绕开这个决定。

### 2.5 DSH 的鉴权不被绕过

**保证**：远程访问 DSH 时，DSH 要求的鉴权一次不少地被执行。

- daemon 自己用就绪行中的进程令牌换取 DSH 的授权 cookie，之后以 `127.0.0.1:<port>` 这个 authority 代理请求。
- 我们不使用 `--trusted-host` 放宽 DSH 的 Host 栅栏，也不伪造 `Origin`。
- 远端浏览器**不持有** DSH 的进程令牌；它只持有自己的隧道密钥。

### 2.6 数据最小化

- 中继不持久化任何 payload。
- daemon 本地只持久化：房间身份密钥、已配对设备公钥与元信息（名称、配对时间、最后可见时间、是否允许控制生命周期）。**不持久化**会话内容、代码、或 DSH 凭据。
- 远端客户端本地持久化：自己的设备私钥、房间标识、UI 偏好。会话内容按 DSH 自己的客户端存储策略处理（那是 DSH 的行为，不是我们的）。
- 通知载荷只含事件类型、严重度、时间戳与不透明会话引用（ADR-0006）。类型里没有承载正文的字段。

## 3. 配对

1. 用户在 daemon 机器上执行 `drdshd pair`，或在 DSH 插件界面里触发。daemon 生成 40 位熵的配对码，显示形式为分组大写 base32（去掉 `I`/`L`/`O`/`U` 等易混字符），有效期 **300 秒**。
2. 客户端输入配对码，双方执行 SPAKE2。配对码本身从不传输。
3. 在派生出的密钥之上，客户端证明自己持有新生成的设备身份密钥（Ed25519）；daemon 保存设备公钥，并在回执里把**它实际服务的房间密钥**用 PAKE 密钥密封后交给客户端。
4. 配对码**立即作废**，无论成功或失败（§ 9.4）。这是防在线穷举的主要手段：一次尝试即消耗一个码。

**回执的两条性质**（M1 修正，细节见 `docs/protocol.md` § 6.2）：房间密钥是 daemon 的**长寿命**秘密，而配对房间中继可读，所以它不能明文过线；同时它必须是 daemon **实际在服务**的那个密钥，否则设备拿到的是一把没人认的钥匙——这正是修正前的行为，也是"配对成功了却连不上"的成因。

**在线猜测的边界**：40 位熵意味着任何单次猜测的成功率为 2⁻⁴⁰。真正的风险不是密码学，而是**实现层的速率限制是否真的存在**。因此：

- daemon 对配对尝试做速率限制与失败计数，并在审计日志中记录；
- 配对码只在显式请求时才生成，不存在长期有效的码；
- M1 的验收项包含"重复使用已消费的码必须失败并有审计记录"。

### 3.1 速率限制的实现与它的诚实边界（M1）

`crates/dr-dsh-crypto/src/throttle.rs` 的 `PairingGuard` 实现三条规则，全部在 **`drdshd pair` 生成配对码之前**检查：

| 规则 | 值 | 为什么是这个值 |
| :--- | :--- | :--- |
| 两次尝试之间的最小间隔 | 2 秒 | 不是安全边界，而是让自动化的"磨"变得可见；没有它，一个重试循环会在一毫秒内耗光整个失败预算 |
| 触发锁定前允许的失败次数 | 5 次 | 人手输入一个 12 位码的容错空间 |
| 锁定持续时间 | 300 秒 | 与配对码 TTL 同量级 |

**状态是文件，不是内存**：`drdshd pair` 是一次性进程，进程内的计数器每次调用都会归零——而这正是攻击者制造的模式。状态写在 `$DSHD_STATE_DIR/pairing-throttle.json`（只有计数与截止时间，没有秘密）。

**三条必须说清楚的边界**：

1. **这不是防猜测的主要手段。** 主要手段是「一次尝试烧一个码」加上 40 位熵：猜测的代价是一个码，而一个码只值一次尝试，所以重试无法把 2⁴⁰ 磨薄。速率限制限制的是**速度**——因为两种代价并不对称：一次猜测花掉攻击者一个来回，却花掉用户一个新码；每秒一千次猜测会在概率移动之前先把用户锁在自己机器外面。所以速率限制同时是**拒绝服务与噪声**控制，`docs/security.md` 从一开始就是这么写的。
2. **锁定会在应用时清零失败计数。** 因此攻击者无法靠"每个窗口失败一次"永久锁死用户。代价是明确的：一个**按节拍**攻击的人每 5 分钟得到 5 次猜测，而不是零次。我们选择让合法用户永远能恢复，而不是追求一个在分布式攻击下本来也不成立的绝对界限。
3. **它按 daemon 全局计数，不按来源。** daemon 只看到中继的一条连接，看不到客户端的真实地址；一个按来源的限流在这里无法诚实实现。因此攻击者可以让合法用户在这 300 秒内配不上对。这是一个真实的可用性缺口，不是疏忽。

**实测**（2026-09，真实中继 + 真实 `drdshd pair`，`DSHD_STATE_DIR` 指向临时目录）：连续 4 次无人认领的尝试被允许，第 5 次触发锁定并打印 `too many pairing attempts; wait 300s before trying again`，第 6 次**在生成配对码之前**被拒绝（输出中没有 `code:` 行），锁定截止时间写进文件并在进程退出后仍然生效。

### 3.2 浏览器端的 SPAKE2（M2 新增）

配对曾经在浏览器里**不可用**：WebCrypto 没有 SPAKE2，也没有可达 Ed25519 群的路径，而当时的结论是"给浏览器做一套简化握手意味着两套安全性质不同的配对协议，比诚实地不可用更糟"。M2 改变的是实现方式，不是协议：

- **协议仍是同一个 SPAKE2**，参数、盲化点、transcript 与 `spake2` crate 逐字节相同，由 Rust 生成的向量固定（`packages/crypto/conformance/pairing-vectors.json`）。
- **只有群运算在 TypeScript 里重写**（`apps/pwa/src/ed25519.ts`）：BigInt 的扩展坐标加法、标量乘、压缩点编解码，公式取自 Hisil–Wong–Carter–Dawson。正确性由 RFC 8032 的公钥向量、群阶、编码往返与那套跨语言向量共同固定。
- 被否决的两条路记在这里，免得后来者重新走一遍：**(a) 把 `spake2` 编译成 WebAssembly** 能保持只有一份实现，但客户端包里会多一个二进制，且中继的内容安全策略必须为 `wasm-unsafe-eval` 开口——而那条策略存在的理由正是这个页面在保管密钥；**(b) 另造一套浏览器专用配对协议**就是上面那句"更糟"。

**这套实现不是常量时间的，也不假装是。** BigInt 没有固定时间运算，标量乘的耗时随标量变化。要诚实地界定它的后果：

- 泄露的对象是**一次性的配对码**，它 5 分钟后过期，且就显示在操作者自己的屏幕上；
- 能在本机测量这段耗时的攻击者，已经在这台设备上，可以直接读屏幕；
- 远端（含中继）无法参与：整个计算在客户端本地完成，网络上的字节与耗时无关。
- **daemon 侧没有任何一行这样的代码**：它继续用 `curve25519-dalek`。登记表、授权判定与所有长期密钥都在那一侧。

**审计员应当检查的三件事**：(1) 群运算与 Rust 实现的一致性（跨语言向量 + 真实 daemon 上的一次完整配对）；(2) 客户端是否在**任何**失败路径上都不写身份文件（`apps/pwa/src/pair.ts` 的 `finally` 只关连接，写盘发生在调用方）；(3) 回执密封的 AAD 是否真的绑定设备公钥（`pairing.test.ts` 里有"换一个身份就打不开"的断言）。

## 4. 审计与可观测性

**记录什么**：隧道建立与断开、配对成功与失败、设备撤销、生命周期操作（谁、何时、结果）、以及配置校验失败。每条记录包含时间、事件类型、设备 id、结果。

**不记录什么**：会话内容、代码、提示词、文件路径、DSH 凭据、任何 payload。

**M0/M1 阶段的存储位置**：daemon 的结构化日志（stdout/stderr，由用户的进程管理器收集）。保留策略（保留多久、是否可选上送、是否需要轮转）在 `docs/product/mvp.md` § 六中列为未决事项，落地前不会默认上送任何地方。

**已实现的形状（M1）**：一行一条 `audit event=<事件> [device=<id>] reason=<原因>` 写 stderr。目前的事件：

| 事件 | 何时 | 带 device |
| :--- | :--- | :--- |
| `pairing_refused` | 限流在生成配对码之前拒绝了一次尝试 | 否 |
| `pairing_failed` | 一次配对交换失败（含超时） | 否 |
| `pairing_locked_out` | 本次失败触发了锁定 | 否 |
| `pairing_accepted` | 设备成功登记 | 是 |

**原因文本会被净化**：控制字符替换为空格、截断到 200 字符。原因来自错误消息，而一条能被换行拆成两行的记录就不再是一条记录——一个日志注入尝试会把诊断信息变成伪造记录。

**尚未实现**：隧道建立与断开、设备撤销这两类事件还没有落到这个格式上；目前它们走 `tracing`。这是 M1 的剩余项，不是已完成的声明。

## 5. 不保证什么，以及剩余风险

这一节是本文档最重要的部分。

### 5.1 中继在客户端的可信计算基里（最诚实的弱点）

**远程客户端（PWA）由中继提供。** 因此一个被攻破的中继，或者一个恶意的托管中继运营者，可以**向一台新设备投递被篡改的客户端代码**——一旦客户端代码被篡改，端到端加密对它就不再有任何保护意义，因为它可以在加密之前把明文送出去。

我们不做"端到端加密所以万事大吉"的声明。缓解手段如下，且每一条都有代价：

1. **客户端包的哈希固定与变更提示。** 客户端在首次配对时记录应用包的哈希，之后若发生变化则明确提示用户，而不是静默升级。代价：正常的版本升级也需要用户确认。
   **⚠ 尚未实现。** 这一条在这里是**计划**，不是现状；M1 的威胁模型走查（§ 5.7）把它记为不成立项。在它落地之前，请不要把它算作已有的缓解——目前真正生效的只有第 2 条（自托管中继）。
2. **自托管中继。** 应用壳由用户自己的基础设施提供时，中继运营者与用户是同一个人，风险回到"你的服务器是否可信"。这是自托管的首要理由，不只是隐私偏好。
3. **可复现构建与独立校验。** 目标是让任何人都能重建客户端产物并比对哈希。这是 M5 审计范围内的交付物，目前**尚未做到**。
4. **原生客户端（未来）**：一个从应用商店安装、由操作系统验证签名的原生 App 可以把中继从这条链路上移除。这是 M3 之后评估原生 App 的主要理由，而不是性能。

### 5.2 元数据泄漏

中继（以及任何观察网络的人）能看到：连接时间与时序、房间标识、流的数量与变化、每帧的长度。这些信息足以推断"有人在用远程访问""活跃程度如何""大概在传输多少数据"，但不足以推断内容。

这是字节转发架构的固有代价。我们**不做**流量填充（padding）或时序混淆，理由是：它们会显著增加延迟和带宽，而收益只是对抗具备长期观测能力的对手——对本项目的目标用户而言不划算。这个取舍是显式的；如果未来有用户需要它，它应当是一个明确可选项，而不是默认行为。

### 5.3 已配对设备被攻破

一台已配对设备的私钥不可导出，但设备本身被完全控制时，攻击者可以**使用**该设备（而不是导出密钥）来访问 DSH。可撤销性是唯一有效的应对：用户在 daemon 侧撤销该设备，撤销即时生效并断开其隧道。设备列表、重命名与撤销在 M1/M2 范围内。

### 5.4 通知的隐私边界

- 隧道内的通知载荷已最小化，不含会话内容。
- **Web Push 默认关闭。** 启用时，载荷经由浏览器厂商的推送服务；即使用了载荷加密，其端到端性质取决于浏览器与推送服务的实现，我们**不**把它当作端到端通道。因此启用 Web Push 时只发送事件类型与不透明引用，正文在用户打开后通过隧道取回。
- 通知在锁屏上的可见性是用户可控的：默认只显示"有事件"，不显示会话标题。

### 5.5 非回环带来的 DSH 侧降级

DSH 客户端把非 loopback 页面判定为"不是操作者本机"，因此部分依赖该判定的设置面板会降级（例如设置持久化退回内存）。这不是安全问题，而是能力限制，但它会导致"设置改了不生效"这类困惑，因此在 `docs/operations/troubleshooting.md` 中显式说明。

### 5.6 daemon 的本地暴露面

daemon 需要一个本地控制端点（供 DSH 插件上报事件、供本地 CLI 查询状态）。该端点：

- 只监听回环地址；
- 需要本地令牌；
- 只接受固定的几种上报与查询，不接受任何会转发到 DSH 的任意请求。

本机上的其他用户如果同时拿到令牌，可以读取状态与写入伪造事件（不能读取会话内容）。这是刻意接受的小风险：把端点做得更复杂（例如 unix socket + 权限位）会提高跨平台成本，而收益有限。M2 会重新评估是否需要 unix domain socket。

### 5.7 M1 威胁模型走查（逐条对照实现）

M1 的完成标准包含「威胁模型定稿」。定稿的动作不是重写，而是**逐条把文档里的断言拿回代码里验一遍**，并记录哪一条在写这份文档时其实不成立。

| 文档中的断言 | 实现中的依据 | 本轮走查结果 |
| :--- | :--- | :--- |
| 中继零知识，且在**构建期**被强制（§ 2.1） | `cargo tree -p dr-dsh-relay` 中没有 `dr-dsh-crypto`、`aes-gcm`、`ed25519`、`x25519`、`sha2`、`hkdf`、`hmac`、`spake2` 中的任何一个；`crates/dr-dsh-relay/tests/zero_knowledge.rs` 把这条固定成会失败的测试 | 成立 |
| 中继不触碰 payload 语义（§ 2.1） | `the_relay_never_reaches_for_payload_semantics`：中继只做帧头校验与转发 | 成立 |
| 只有一处代码能 import DSH（§ 2.5） | `pnpm run lint:imports` 扫描 25 个 TS 文件，只有 `plugins/dr.dsh/src/dsh-surface.ts` 允许 | 成立 |
| 只有配对客户端与本地 daemon 能读到内容（§ 2.2） | 会话密钥由盐派生、经 AEAD 封帧；**M1 新增**：设备认证在 `established` 置位**之前**完成，因此不存在「可用但未认证」的连接 | 成立（本轮加强）；**但走查漏掉了配对房间**，见下面的第 3 条 |
| 未配对设备无法建立隧道（M1 验收项） | `DevicePolicy::Enrolled` + `resume_challenge` 挑战—应答；真实栈实测：登记 1 个设备后 room-key 客户端被拒并得到具名原因 | 成立 |
| 配对码单次且过期（M1 验收项） | `PendingCode::consume` 在 SPAKE2 之前烧码；`an_expired_code_is_refused_and_stays_refused` | 成立 |
| 在线尝试必须被速率限制（§ 1 表格、§ 3） | 见 § 3.1；本轮之前**不成立**——文档承诺了实现层并不存在的限流 | 本轮补齐 |
| 审计记录配对成功与失败（§ 4） | `pairing_*` 四类事件；隧道建立/断开与设备撤销**尚未**落到该格式 | 部分成立 |
| 客户端包哈希固定与变更提示（§ 5.1 缓解手段 1） | 没有实现 | **不成立**，见下 |

**本轮走查发现的两个不成立项**：

1. **速率限制曾经只是一句承诺。** § 1 的表格与 § 3 都写着「在线尝试必须被速率限制」，而在这轮之前，代码里没有任何限流：任意快的尝试都会各自拿到一个新码。这不是「尚未实现」的疏忽，而是**文档断言了代码没有的东西**——审计时这类条目比缺失的功能更危险，因为它会让读者以为风险已被处理。现已落地并有实测（§ 3.1）。
2. **客户端包哈希固定仍未实现。** § 5.1 把它列为「中继在客户端 TCB 内」的第一条缓解手段。它至今没有落地，而 § 5.1 的措辞容易让人读成"已有缓解"。**现状是：这条缓解手段不存在**，中继投递被篡改的客户端代码这一风险目前只由「自托管中继」与「可复现构建（M5）」两条缓解，且后者也未完成。这是本项目当前最诚实的弱点，在 M5 之前不应被表述为已缓解。

**走查之后补记的第 3 条（第 27 轮）：配对回执曾经把房间密钥交给中继。**

§ 2.1 在走查时已经写上了「配对房间的传输根是公开常量、中继读得到它」，而走查**没有把这句话推到它的结论上**：回执里的 `root_key` 就是明文过线的，而它当时还是设备将要使用的房间密钥。于是「只有配对客户端与本地 daemon 能读到内容」在配对这一步上是**不成立**的——中继可以把每个新设备的房间密钥记下来。

教训值得写下来，因为它不是「忘了检查某一行代码」，而是**走查的粒度错了**：那张表逐条对照的是"这条断言有没有依据"，而不是"每条通道上流过什么"。一条被声明为"不保密"的通道，需要紧接着问一句"那么什么可以流过它"，而这一步当时没有做。现在这一问写在 § 2.1 里，并由 `the_relay_cannot_read_the_room_key_out_of_the_receipt` 固定住。

**走查结论**：除上述三项外，文档中的其余断言在实现中都能找到会失败的测试作为依据。M1 的威胁模型据此定稿（第 27 轮补记第 3 条）；下一次走查安排在 M2 结束（实现评审，重点是生命周期管理引入的新攻击面）。

### 5.8 浏览器存储与同源边界（第 28 轮）

**第 38 轮补充（ADR-0007 之后）**：浏览器里存的东西从"一条记录（身份 + 房间密钥）"变成"**一条身份 +
每房间一条记录**"。安全含义有两点：一是私钥仍然只有一份（每多存一份就是一个多出来的泄露面），二是
多出来的房间密钥与房间 id 让"这台浏览器与哪些 daemon 配对过"成为存储里的可见事实——它本来就在
`drdshd devices` 那一侧可见（每个 daemon 都能列出设备），现在两侧一致。IndexedDB 从 v1 升到 v2 时，
旧记录被拆开并且**旧存储被删除**：升级不保留第二份私钥。同一节开头那条边界（外壳与被代理的 DSH 界面
同源，因此界面里的脚本能读到这些）没有变化，仍然是这个架构里最诚实的弱点之一。

配对结果必须存在浏览器里，否则「配对一次」只在本次访问内成立。存的是**长期密钥**：设备私钥（PKCS#8）、房间密钥、device id 与房间。它保存在 **IndexedDB**（`apps/pwa/src/storage.ts`）而不是 `localStorage`——后者是一个同步字符串表，源内任何一段同步脚本都能在任何时刻读它。

**但存储介质不是这条边界的全部，真正的边界是源。** 外壳与**经隧道送达的 DSH 界面**共享同一个源：界面的路径是 `/__dr/interface`，它的资源也由同一个 host 提供。因此：

- 这段记录**对 DSH 页面自己的 JavaScript 可见**。DSH 是本机上的用户自己的程序，所以这不是"把密钥交给第三方"；但它是"把远程访问的长期凭据暴露给一个会执行任意插件代码的页面"，这句话应当被读一遍再决定是否接受。
- Service Worker 的拦截同样按源工作，因此界面能到达的一切，外壳也能到达，反之亦然。
- 真正的隔离需要一个**第二个源**（另一个端口或另一个主机名），中继目前不提供，也不打算在 MVP 内提供：那会要求用户在浏览器里接受两张证书、或在部署文档里解释两个地址。

**这件事没有被"修掉"，只是被写清楚了。** 在 M5 的审计范围里，它是"客户端代码与凭据存储"这一项的输入；如果审计认为不可接受，出路是让中继同时监听第二个端口只服务界面，而不是把密钥换个地方存。

### 5.9 M2 结束的实现评审：生命周期引入的攻击面（第 31 轮）

`docs/product/mvp.md` § 四把「M2 结束」定为一次实现评审，并点了三个问题。这一节是那次走查的记录：
每个问题都对照代码找出**会失败的测试**，而不是只读一遍。

| 问题 | 实现依据 | 结论 |
| :--- | :--- | :--- |
| 子进程启动参数是否可能被远端影响 | 子进程只由 `SupervisorConfig { executable, port }` 决定，两者都来自 daemon 自己的命令行；命令行的形状是固定的 `dsh web --no-open --port <p>`（`crates/dr-dsh-daemon/src/dsh/supervisor.rs`）。远端唯一能送到驱动的东西是 `LifecycleOp`，一个 serde 枚举。 | **不受影响**；`no_operation_can_carry_an_argument_into_the_driver` 用六种走私形状（命令串、对象、数组、数字、null、空串）断言"拒绝且**不触达驱动**"，`scripts/pwa-control-smoke.mjs` 再在真实隧道上断言一次同样的事 |
| 白名单是否真的闭集 | `LifecycleOp` 是 `start`/`stop`/`restart` 三个变体，**没有 `#[serde(other)]` 兜底**；控制面只回答 `status_request` 与 `lifecycle_command`，其余一律 `problem`（`crates/dr-dsh-daemon/src/control.rs`）。客户端另有一份自己的白名单，属于纵深防御而非唯一防线。 | **闭集**；单元测试 + 真实栈各一层 |
| attach 模式是否有绕过路径 | `Mode::Attached` 的 `refusal_reason()` 覆盖全部三个操作，且 `check_permitted` 在**驱动之前**拒绝——拒绝是内联回答的，进程根本不会被碰；`owned` 由 mode 推导（不是可以分歧的第二个字段）；attach 的凭据由操作者提供，不读 DSH 自己的凭据存储（ADR-0003）。 | **无绕过路径**；`a_lifecycle_command_is_refused_with_its_reason_in_attach_mode` 与真实栈上的控制面冒烟（三个操作各被具名拒绝）覆盖 |

**本轮走查发现并修复的一个真实缺陷：就绪行里的令牌曾经可被打印。**

`ReadyLine` 派生 `Debug`，于是 `tracing::debug!(?ready)` 会把 DSH 的一次性进程令牌原样写进日志；
更隐蔽的是 `ReadyParseError` 的三个变体把**它们读不懂的那一行**引用进错误消息（`not a readiness line: {0:?}`），
而那行里就带着 `?token=`。两条都违反了本仓库自己那条"不要在日志、Debug、错误信息里打印密钥"的规则——
规则被应用到了"持有密钥的类型"，却没被应用到"引用原文的解析错误"。

修法：`ReadyLine` 手写 `Debug`（令牌打码、端口保留），解析错误统一走 `redact()`（把 `token=…` 折叠成
`token=<redacted>`，并截断长度）。回归测试 `a_credential_never_appears_in_a_parse_error_or_a_debug_print`
对三个引用原文的错误变体与 `ReadyLine` 的 `Debug` 各断言一次；**把修复改回去这个测试会红**（验证过）。

**评审明确保留的剩余风险**（不是遗漏，是已知并接受）：

1. **已配对设备可以反复下发 `restart`。** 驱动串行处理命令（一次只有一个进程操作在飞），但没有任何限流：
   一台被拿走的设备可以把 DSH 反复重启。它落在"拿到已配对设备就等于拿到本机操作权"的边界内——那台设备
   本来就能执行 DSH 的一切——因此不在 MVP 内修，但**写在这里**，因为"远程能重启"和"远程能无限重启"
   是两个不同的说法。
2. **`--attach-token` 走命令行**会出现在 `ps` 与 shell 历史里。安装文档已经建议用环境变量或 0600 文件，
   但 daemon 自己不强制；M2 的评分标准没有要求它，记在这里以免被读成"已经处理了"。
3. **Windows 上没有优雅停止**：daemon 无法向 DSH 发送 SIGTERM 的对应物，DSH 被直接终止，插件树不走销毁
   流程。差异写进 `docs/operations/install.md`，解决它需要平台特定实现（M2 收尾项）。

### 5.10 崩溃上报的边界（M5）

M5 的完成标准里有"崩溃上报可用"。这一节写清楚它**是什么**、**去了哪里**、以及**不包含什么**，因为
"上报"这个词在别的项目里通常意味着一个服务器。

**没有服务器。** 报告只走一跳：客户端 → 它已经配对的那台 daemon（密文隧道内）→ 该 daemon 的状态目录里
一个 0600 的文件（`$DSHD_STATE_DIR/crash-reports.jsonl`）。没有可配置的上传端点，没有第三方接收方，
也没有任何自动发送的路径。项目定义 § 9.5 的数据最小化与 ADR-0006 的"默认关闭"是同一立场的两个面：
一个会替用户把失败片段寄出去的功能，与这个项目存在的理由相矛盾。

**报告里有什么**（`dr_dsh_proto::control::CrashReport`，字段是完整清单）：

| 字段 | 内容 | 为什么它在里面 |
| :--- | :--- | :--- |
| `client` | 客户端与版本，如 `pwa 0.0.0` | 一份不知道来自哪个构建的报告无法归因 |
| `phase` | `loading` / `pairing` / `connecting` / `ready` / `offline` / `stopped` | "坏在哪里"是报告要回答的第一个问题 |
| `reached_ready` | 这一次运行是否**曾经**可用 | 没到达可用状态却没有任何 error 事件，正是报告存在的理由 |
| `errors` / `rejections` | 未捕获错误与未处理 rejection 的**计数** | 计数是准确的；文本是截断的 |
| `samples` | 最多 20 条、每条最多 200 字节的失败描述 | 一句话足够定位；整份日志是另一回事 |
| `user_agent` | 浏览器 UA，截断到 200 字节 | 浏览器差异是前端崩溃的常见成因 |
| `at_ms` | 生成时刻 | 与 daemon 日志对齐时间线 |

**报告里没有的**（不是"目前没有"，是类型里没有字段可放）：房间密钥、设备私钥、配对码、会话内容、
消息文本、DSH 的令牌、cookie，以及任何 URL。有一条现实边界要写清楚：**一段错误消息本身可能包含 URL 或
文件路径**，所以 `samples` 按 200 字节截断、控制字符被替换（`apps/pwa/src/health.ts` 与
`crates/dr-dsh-daemon/src/crashlog.rs` 各做一遍：前者保护隧道与日志，后者保护文件）。

**谁在防谁**：客户端是**刚刚失败的那个组件**，所以它的保证不算数。daemon 自己重新校验每一条边界
（样本条数、每条长度、整份报告的序列化长度、控制字符），超限就**具名拒绝**而不是截断后收下——
一份少了两百条失败的"报告"在撒谎。文件最多 20 份，满了之后**拒绝而不是淘汰**：被淘汰的那份正是有人
正在找的那份，而 `drdshd crashes --clear` 是人能执行的恢复动作。

**用户怎么拿到它**：`drdshd crashes`（在那台机器上）打印原文，`drdshd crashes --clear` 删除。实测见
`docs/product/mvp.md` § 五点六六；`scripts/pwa-crash-smoke.mjs` 9/9。

**明确的缺口**：上报需要隧道。**在连上之前就坏掉的页面**（例如模块加载失败）能记下失败，却无处可送——
下一次成功连接才会把它送出去，而如果这一轮从未连上，报告就只留在页面内存里直到标签页关闭。这是传输
本身的性质（没有会话就没有信道），写在这里以免被读成"任何崩溃都会被上报"。

### 5.10.1 审计日志的隐私边界（第 38 轮实现）

ADR-0012 决定、第 38 轮实现的审计日志，落点是 `$DSHD_STATE_DIR/audit.jsonl`（**0600**，30 天 / 10 000 行
滚动）。它记录的是**事件而不是内容**，字段只有五个：`at_ms`、`event`、`device`、`outcome`、`reason`。
事件是闭集：配对四类、`device_revoked`、`tunnel_established`、`tunnel_released`、`lifecycle_command`。

要如实说明的三点：

1. **它是一份"谁在什么时候用了这台机器"的记录。** `tunnel_established` 带设备 id 与时间，多次重连就是
   多条记录。它写在本机、0600、可删除、也可以整个关掉（`DSHD_AUDIT=0`），但**默认是开着的**——
   一个只在有人记得打开时才存在的审计日志，不是审计日志。
2. **`reason` 是自由文本。** 它来自错误消息，因此可能包含路径或主机名（与崩溃报告的边界相同）。
   已做的处理：控制字符被替换（防止一行变两行、或往终端里塞转义序列）、长度截到 200 字节。
   **没有做**的是内容审查——审计日志的用途正是把话说清楚，一条被清洗到看不出原因的记录没有价值。
3. **它从不离开这台机器。** 不上中继、不上托管服务、不经隧道发给客户端；读取方式是 `drdshd audit`，
   把它交给别人必须是人的动作。读取端同样应用 30 天窗口（机器很久没跑 daemon 时文件里可能还有更旧的
   记录，`--clear` 可以真正删掉），而**读不出来的行会被保留并上报**——删掉它等于销毁"有人写了一行
   解释不了的东西"这个事实。

写失败（磁盘满、目录被删）只打印一次警告，服务照常——把"日志写不下去"变成"隧道不可用"是一种可利用的
拒绝服务。代价是"审计其实没在记"可能很久没被发现，所以 `drdshd doctor` 会报告当前状态与最后一条事件。

### 5.11 第三方审计的准备状态（M5）

M5 的完成标准里有一条"审计无高危"。**这条不能由本仓库自称**：它是外部结论，而目前**没有**进行过第三方
审计，所以进度行里它是**未达成**，不是"已完成"。本轮做到的是把审计可以开始所需的东西准备好——范围、
材料清单、每条安全声明对应的"改坏就红"的检查、以及我们自己的高风险候选清单——写在
[`audit-scope.md`](audit-scope.md)。那份文档本身也接受审计：**如果某条声明在那里找不到强制手段，那条
声明就是散文**，请按发现报出来。

## 6. 密码学清单

| 用途 | 算法 | 实现 |
| :--- | :--- | :--- |
| 配对密钥协商 | SPAKE2（平衡 PAKE） | Rust `spake2`；TS 侧见 ADR-0004 的向量约束 |
| 设备身份 | Ed25519 | Rust `ed25519-dalek`；浏览器 WebCrypto |
| 密钥派生 | HKDF-SHA256 | Rust `hkdf`/`sha2`；WebCrypto HKDF |
| 密钥协商（会话） | X25519 | Rust `x25519-dalek`；WebCrypto X25519 |
| 内容加密 | AES-256-GCM | Rust `aes-gcm`；WebCrypto AES-GCM |
| 随机数 | 操作系统 CSPRNG | `getrandom`；`crypto.getRandomValues` |
| 常量时间比较 | — | Rust `subtle`；浏览器侧不自行实现 |

设计约束：

- **不自行实现密码学原语。**
- **不使用非标准的构造**：标签与派生链在 `crates/dr-dsh-crypto/src/lib.rs` 的 `labels` 中集中定义，改动标签等同于 wire-breaking change。
- **nonce 不复用**：每条流每个方向一个单调计数器；计数器回绕（理论上在 2⁶⁴ 帧后）应当强制重建连接，而不是继续使用。
